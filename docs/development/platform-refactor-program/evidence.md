# Evidence, Verified at Source

This annex is part of the [Platform Refactor Program](../platform-refactor-program.md).

## What the evidence says

This section is built only from rows of the evidence annex that are marked CONFIRMED or CORRECTED. The number in square brackets is the row.

**The journey.** The oldest of the five repositories was first committed on 2026-02-22, and the youngest, bc-db, on 2026-09-09 [1]. A metric contract version is one versioned definition of a metric. The platform database holds 463 of them, and 93 are in the governance state `active` [2a]. Of the 463, 430 were created in June and July [2b]. No version has moved to `active` since 2026-09-30 [2c]. A proof pin is the record that a metric's governed value matched an independently worked expected value on a demo world. The proof pin table holds four rows, for three metric contracts, all created between 2026-10-31 and 2026-11-10 [3]. Five bc-db migrations each create a table named for one canonical contract version, and 16 of the 67 platform migrations name such a table [4a, 4b, 4c]. Six of these tables exist in schema `demo`, and three hold rows [5]. The choice of world, contract version and evaluation date for a proof is written in three TypeScript files, so changing a pin means changing code [6]. Over the same weeks the approval desk recorded 430 grants [7].

**The code.** Three breaks are on the main route. First, the forward route from a connector to its source tables joins reader bindings to source contracts. All 19 reader bindings hold admission contract identifiers, so the join returns nothing [9]. Second, the DevHub metric drive still calls the direct activation route, and the DevHub metric recipe names that route as its last step. bc-core answers it with HTTP 410 Gone [10a, 10b, 10c]. Third, the served route `POST /tenants` refuses by design, and the working act is a command. Four bc-docs documents and CLAUDE.md still name the served route [11a, 11b, 11c]. The HTTP route for a new canonical contract version cannot declare the grain pin or the legal-entity key form. The service accepts both, and only one runner passes them [12].

The DevHub hotspots page reports that 731 of 2,610 scanned bc-core files pass every checked rule, that 542 share duplicated blocks with other files, and that 31 files exceed 1,000 lines [13]. The file changed most often in the last 30 days is the canonical resolver, with 20 commits [13]. bc-core holds 681 files under `scripts`, and 445 of them are under `scripts/archive` [14]. The frozen-module registry lists nine modules, and eight of them no longer exist [15]. Three lines carry a committed credential (one account password on two lines, and one API key), and 68 more carry a local database password [17a, 17b]. Three global guards carry a bypass: the role guard lets `super_admin` and `admin` pass every role check, and the scope guard and the tenant-claim guard let `super_admin` pass [18].

The platform database holds 22 schemas and 329 tables, and 77 tables are empty [16a]. It holds four tenants, and only the fixture tenant `kaveri` is `active` [16b]. It holds no table for a subscription or an entitlement [16d]. The one package table lists readers, not metrics [16c]. bc-infra defines six stacks, and three were found deployed [19]. The twelve repositories carry 323 linked worktrees, 239 of them in the folder `~/MyProjects/_wt`, and the served build runs from one of them [20a, 20b].

**The documents.** bc-docs already holds the pieces of a functional map. The platform-readiness chapter lists 19 functions under the heading "The platform functions — the stable spine" [22]. The vocabulary page holds the tenant-side ladder and a six-condition definition of "done", and it retires "onboarded" and "validated" used alone [23a, 23b, 23c]. By the documents' own rule none of this binds. A chapter binds only when it is authoritative and locked, and none of the 124 chapter files in the nine section folders is locked [21a, 21b]. The chapters annex counts 131 files because it also covers the seven files under `docs/archive`; none of those is locked either.

Delivery to a tenant is designed and not built. The Subscription is defined as a platform record with four entitlement axes [25b, 25c]. The enforcement chapter lists eight surfaces and marks every one "Not yet wired" [25a]. ADR DEC-c220e4 requires the entitlement record before any tenant is activated for an outside party [24a]. Three chapters each name a different act that puts a metric before a tenant: an adoption record, an entitlement check, and the `active` state alone [26]. The change-classification chapter sends an additive change to bound tenants automatically, and it classes two value-changing edits as minor [27a, 27d].

The procedure chapters have drifted from the platform. Two of the 13 files in `docs/onboarding` name only, or almost only, routes and tables that exist today. Six name mostly ones that do not [28].

The share of checkpoints and plans that cite a chapter path went from 20.7% in May to 0.4% in October [29a]. Commits that touch a chapter went from 107 in September to none in November, and the last is dated 2026-10-12 [29b, 29c]. CLAUDE.md never held a general step to read a chapter; the 2026-09-25 commit shortened the one step about procedure chapters [29d]. Memory loads into every session, and it now runs to 396 files and 280,002 words [30].

**DevHub.** DevHub's pinned anchor is still the parked Demoed drive [31]. Its boot text reports 12,437 candidates as "in-flight", from tracker tables last written on 2026-07-07 [32b, 32c]. Its document index scans a bc-docs working copy that is 141 commits behind origin/main [29e, 33]. Its backlog holds 2,006 open tasks. Of these, 992 are review tasks it created itself, and 56 are marked in progress with no open session [8a, 8b, 8c]. Eleven plans are not closed (ten `active` and one `draft`), and none has changed since 2026-10-02 [8d].

Numbers in square brackets refer to the numbered rows of the annex [Evidence, verified at source](evidence.md). Where a dossier gives a different count for the same thing, it measured something else, and the dossier says so beside the count.

The main document cites a row by its number in square brackets, for example [16a]. Every row was opened on 2026-11-13; the repositories were read at `origin/main` at the short shas in the table below, bc-core at `ec72438b`. **Section 5, "What "done" means" (lines 232 to 249), in full:**

> "Two words, for two different things.
>
> **Done, for one metric on one tenant.** A metric is done for a tenant when all six hold, and each is read from its record on the day it is claimed:
>
> 1. It is **certified** and **released**.
> 2. It is **enabled** for that tenant, by the governed onboarding act alone.
> 3. It is **reporting** for a stated period, by the governed evaluation act alone, with the proof that act writes.
> 4. That value **agrees with the expected value** worked out independently from the same source data for the same period, and the agreement is written down where it can be read again.
> 5. A tenant user **sees that value** in the portal, checked in the running application.
> 6. **No workaround was used at any step.** A direct edit, a bypass, an override, a hand fix or a one-off script at any step means the metric is not done, and the step's owner has a defect to fix.
>
> **Proven, for the route.** The way metrics are produced is proven when, in the operator's four conditions: (a) it used the mandated route alone; (b) it repeats from a clean start by the written procedure alone, in a session that did not build it; (c) each stage and each handoff has its own tests that can go red, kept and re-run; (d) a second, different case passes with no change to any stage.
>
> So "a Kaveri-proven metric" means: a metric that is **done for Kaveri**, through a route that is **proven**. One metric going green does not prove the route, and a proven route does not make any one metric done.
>
> **No record holds "done" today.** Until one does, "done" is written only together with its six reads and their date. Section 8 names this as the first thing to build."
