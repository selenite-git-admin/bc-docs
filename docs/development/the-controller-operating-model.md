# The Controller Operating Model

**Status of this chapter.** The fleet described here is decided (ADR DEC-41e4bc, `decided`, 2026-09-30) and is rolling out by phase; only the phase-0 availability scripts have merged, and phases 1 to 4 are not built. The roster of thirteen controllers is the operator's amendment of the ADR's twelve, recorded as erratum ADR-ERR-004. On 2026-09-30 the operator approved the nine recommendations of the research report "Controller charters from documentation" (where this chapter lives, how the roster is recorded, one authority vocabulary, the dead citations, the auditor as a Compliance control, the canonical portal design, DEC-96cc78, the documentation reader, and the provisional human role map); this chapter records them as decided, and the human role map remains provisional until people are named.

## Scope

This chapter defines the controller operating model: the fleet of controller sessions that owns BareCount's engineering work, the collective rules the fleet runs under and how far each rule has rolled out, the escalation ladder, the roster of thirteen controllers with one charter each, and the way a controller's working brief derives from its charter. It is written for a person taking a role in the fleet with no prior context, and it presents the fleet as a rollout in progress, not as an as-built system, because the Development section does not present an aspirational engineering posture as if it were the as-built.

This chapter leaves three things to other chapters. The registry substrate that records sessions, tasks, plans, decisions, change records and review verdicts is the DevHub chapter. The procedure for recording an architecture decision record and the plan-and-report change-record pair is the Decision and Change Procedure chapter. The operation of the independent auditor (what runs on the Mac Mini, who authorises what, how to re-arm, upgrade or roll back the service) is the Mac auditor runbook, `operations/mac-auditor-operations.md`. The documentation integrity register (the punch-list of stale documents with an owning controller per row) and the operator's nine open decisions live in the research report named above; this chapter references them and does not reproduce them.

**Governing source.** DEC-41e4bc; Development: Overview ("What Development Means").

## The Fleet

The fleet is a set of long-lived Claude sessions, each answering for one area of the platform, coordinated by one of them and enforced by the coordination registry. The terms below are used throughout this chapter with these meanings.

| Term | Meaning |
|---|---|
| Controller | A long-lived Claude session that owns one area of the BareCount platform: its documents, its repositories, its live systems, and the judgement rules that govern changes there. Each controller later reports to a human role |
| Worker | A short-lived session that a controller spawns for one bounded task. A worker names its controller when it opens |
| Chief | The controller of controllers. It runs the daily rhythm with the operator, routes work that no controller maps to, and holds the escalation ladder |
| Operator | The founder, today the only human in the loop. The operator talks to the Chief and the controllers, never to workers, and is the only source of authority for live acts |
| DevHub | The coordination registry: a Node and SQLite server on port 4000 (repository `barecount-devhub`) that records sessions, tasks, plans, decisions, change records and review verdicts and enforces the session-close gates. The DevHub chapter describes it |
| Session | The unit of governed engineering work in DevHub. A session is opened, carries a saved plan, records checkpoints, and closes with a report and a self-audit |
| Task | A unit of work recorded in DevHub (`TSK-xxxxxx`), with a lifecycle of parked, planned, in progress, and completed, aborted or failed |
| ADR | An architecture decision record, a file under `docs/governance/adrs/ADR-{uid}.md` in bc-docs, identified by a `DEC-xxxxxx` UID. ADR files are the source of truth for decisions; DevHub holds metadata (DEC-a4e550) |
| bc-docs | The documentation repository and the single source of truth for platform documentation, under `docs/` |
| bc-core | The platform's engine and API service, served on port 3100 |
| Codex | The independent auditor: a separate model session that reviews engine changes it did not author. It runs on the Mac Mini under the macOS account `bcauditor` (DEC-44456d) |
| The gen- exchange | The permanent message protocol between a session and Codex (DEC-081931). Threads are named `gen-xxxxxx`; a session publishes a message and waits for a protocol-valid reply |
| The desk (bc-exchange) | The auditor exchange desk, a service on port 3040 running as `bcauditor`, where the operator records grants. A request on the desk is never authority; only a recorded grant is |
| Grant | An operator authorisation recorded on the desk by entering the current six-digit code from an authenticator app. Every grant carries the SHA-256 of its text and a `grant_id` ending in the first eight hex characters of that hash |
| Serve move | The governed procedure that puts a pinned bc-core build (one detached worktree per served commit) on the live port 3100. It needs a review and an operator grant |
| Live window | The announced period during which a serve move, a database apply, or both are performed on the live host |
| Foundation | The architectural authority of the platform: the chapters under `docs/foundation/`, above all the six invariants and the authority model |
| MCF, MCV | The metric context framework (the `mcf` database schema and the bc-core services that author, certify, activate, bind and evaluate metric contracts) and a metric contract version, one governed version of a metric contract |
| Live tenant | `kaveri`, the only active tenant; the demo world it observes runs in Odoo on demand |

### Controllers, workers, the Chief and the operator

ADR DEC-41e4bc states the model in one sentence: BareCount work runs as a fleet of controller sessions with short-lived workers, and its rules are enforced by DevHub, not by memory or instructions. Every session declares a role, controller or worker; a worker names its controller; every session binds to exactly one task before it changes anything. Every task and plan has an owning controller. The operator talks to the Chief and the controllers, never to workers.

The operator has exactly three kinds of act, all verified against the live desk and the runbook. Authority: every live act (a database apply, a serve move, a cloud change, a secret) needs the operator's own recorded grant for that act (`mac-auditor-operations.md`, section 2); merges by Codex through the auditor GitHub App run under recorded grants (`4e95a6b8` for bc-core, bc-db, bc-portal and barecount-devhub; `1bea8fcd` for bc-docs; `22d493f8` for bc-exchange); production applies and any promotion beyond local development are Gate ④, operator-only (DEC-4c1396). Decision: where no document settles a question, the operator's direct word is the authority (ADR DEC-fa7c63). Rhythm: the start-of-day and the wind-down with the Chief (DEC-41e4bc, point 10). A grant is recorded only when the operator enters the current code; the desk's `recordGrant` verifies the code before writing, and all 103 grants on the desk at the time of verification were recorded that way.

### The roster

The fleet is thirteen controllers: Chief, Architect, Platform, Metric, DB, DevHub, Customer Portal, Admin Portal, Infra & CI, Audit, Docs, Demo, and Compliance & Quality. ADR DEC-41e4bc's text names twelve (with one "UI" controller and "Metrics & Onboarding"); the operator split UI into Customer Portal and Admin Portal and renamed Metrics & Onboarding to Metric on 2026-09-30. That amendment exists only in the design document carried by barecount-devhub pull request 148 (a draft, at head `d4a93683`), whose own bullet list still reads twelve names; the ADR is therefore stale on the roster until it is amended or superseded. This chapter follows the operator's confirmed thirteen.

Two existing rule sets carry the same philosophy and bind every controller.

The ten D268 session-discipline rules (ADR DEC-ebf0b4, `implemented`) forbid bulk contract-chain generation, cosmetic status changes and unverified chain wiring; require one-then-many (prove on one before scaling) and independent verification (script output is not proof, the side effect is); and require a self-audit at close, where fabrication of a clean report, not omission, is the violation.

The eight ADR hygiene rules (ADR DEC-623f8f, `decided`) require the supersession pair (when a new ADR supersedes another, the target is flipped to `superseded` in the same commit), flag records stuck in `proposed` after 30 days, tie implementation to `closes: DEC-xxxxxx` commit tokens, and set a monthly audit and a quarterly sweep. Verified enforcement: rule 1 runs on every push and pull request through `.github/workflows/adr-hygiene.yml` running `scripts/docs-control/audit_adrs.py`, and reports zero supersession issues; rule 2 is checked on every run but is advisory only (no `adr-stuck-proposed` task has ever been spawned); rule 4's monthly schedule and `docs/governance/adr-audit-history.md` do not exist. The ADR names a script, `scripts/adr-audit.js`, that does not exist; the live enforcer is the Python auditor named above.

## The Escalation Ladder

ADR DEC-41e4bc, decision point 2: escalation runs worker, then its controller, then the area's owner, then the Chief, then the operator (authority only); an unmapped area goes to the Chief. In plain words: a worker that cannot proceed raises to the controller that spawned it. That controller raises to the controller that owns the area if the blocker is in another area. That owner raises to the Chief if two controllers disagree or the blocker is cross-cutting. The Chief raises to the operator only when authority is needed: a grant, a database approval, a merge, a live act, or a decision no document settles. The operator is not an escalation for work; the operator is the source of authority. Every escalation that reaches the operator arrives as a plain decision with a recommendation.

Review escalation has one more rule, from the Audit area: at most two review rounds per unit, then escalate rather than open a third. The rule is installed as desk rule R3 (grants `6d37cbfc` of 2026-09-28 and `d8b54d8c`) and in the auditor's `barecount-auditor-session` skill; a third round opens only on an explicit grant (`cc4978fb` and `39c87136`, both 2026-09-30). Two bc-docs sentences restate the cap (`development/lessons-platform-readiness-umbrella.md` and `implementation/platform-db-foundation-requirements.md`); neither the Mac auditor runbook nor ADRs DEC-081931 and DEC-44456d state the number.

**Governing source.** DEC-41e4bc point 2; bc-exchange `src/rules.json` rule R3 and the grants it cites.

### Chief

**Purpose.** The Chief exists so that thirteen independent controllers behave as one fleet: work lands on the controller that owns it, nothing important is unowned, escalations reach the operator only when authority is needed, review verdicts are sealed, and the operator sees one start-of-day and one wind-down picture rather than thirteen. Good looks like this: every task and plan in DevHub has an owning controller; the operator's day begins and ends with a brief derived from DevHub data, not written from memory; no controller's close has ever passed on an unverified deliverable; and the cost of running the fleet is known. The Chief has no documentary predecessor: no bc-docs chapter mentions a fleet, a roster or a Chief, and the only artifact is ADR DEC-41e4bc. The design document behind the ADR adds a "Cost Watch" area owned by the Chief (design table row "AWS cost | Infra & CI | Chief | operator"); that unmerged document is the only source for the Chief's cost remit.

**Boundaries.** The Chief never does a controller's work in its place; it routes. It never talks to workers on the operator's behalf. It never records a grant, approves a merge, applies a migration or moves a serve; those are operator acts, and the Chief prepares them as plain decisions with recommendations. It never fakes an override (`l_node_override`, `foundation_gate_override`) and never lets a close pass on "unverified". It never quotes DevHub counts as truth for anything whose truth is a file or a database (decisions, documents, contracts).

**Relationships.** Depends on DevHub (the substrate that will enforce roles, ownership, ledger and close), Audit (the desk where the daily seal grant is recorded), and every controller (their attested verdicts and their closes). ### Architect

**Purpose.** The Architect keeps what is decided (ADRs), documented (bc-docs), coded (bc-core) and stored (the databases) in agreement, with Foundation above all of them. Good looks like this: every Foundation chapter is indexed and consistent with the tree; every ADR's status is truthful and its supersessions are paired; every rule in daily use has a defining document; the architecture gates in bc-core fail on any breach of a frozen boundary; and every cross-controller design question resolves through a named invariant, ADR or erratum rather than through memory. Foundation is the architectural authority: every claim any other section makes about platform behaviour derives from a Foundation chapter, an ADR or an erratum, and Foundation derives nothing from a later section (`foundation-overview.md`). The authority ladder has five levels (DEC-5a9dee): Foundation; the ADR and errata layer; the generated enforcement map (`docs/reference/enforcement-surface-map.md`); the live substrate, which wins as fact while the ADR layer wins as intent; and the descriptive layer, which is never authority. The Errata Ledger is the only admissible form of "X takes precedence over Y until Z" (`docs/governance/errata/README.md`).

## From Charter to Brief

A controller's charter (its subsection above) is durable: purpose, documents, systems, boundaries, relationships, judgement rules. A controller's brief is the charter plus a state capture: the verified current state of its area on a stated date, read from the live sources the charter names (the served commit, the applied ledger, the open pull requests, the open tasks, the grants on the desk), not from memory or from a previous brief. The research report's "Verified current state" sections are the first state captures; each charter above folds the 2026-09-30 capture into its purpose and its systems paragraph. A brief is regenerated whenever the state moves, and its verification pass corrects the charter where the two disagree; the report's own first drafts were wrong in five places (supersessions counted that were zero, a ladder that did not exist, an exclusion called undocumented that was documented, migration numbers read from a stale checkout, a "no contradiction" that hid five), and every error came from reading documents without reading the enforcer, the substrate or the pull request beside them. The fleet's principle, detect, don't trust self-report, applies first to a controller's reading of its own estate.

Before any reset of a controller session, its brief passes a cold-read test: a reader with no prior context, given only the brief and its reading list, can state what the controller is answerable for, what is live now (with the identifiers: commit, ledger row, grant, task), what it never does, and what its next unit of work is. A brief that needs the previous session's memory to be understood has failed the test and is not ready.

**Governing source.** DEC-41e4bc (Principles: detect, don't trust self-report; agents lift and controllers verify); the research report's Part A.5 and Conclusion.
