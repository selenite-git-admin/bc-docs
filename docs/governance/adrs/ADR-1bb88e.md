## Decision

Under DEC-89db41 D1 (Demoed is proven end-to-end in ONE in-platform demo plane, never crossing into a tenant) and D3 (demo.* holds only the platform's own declared synthetic demo data, entering through an owner-plane synthetic-only ingress whose customer-lineage check gates visibility, fail-closed), the demo runtime plane (schema demo.* inside bc_platform_dev, RuntimePlane{kind:'demo'}) SHALL be a RESOLVING plane — generalized from today's CO+MS EVAL plane over pre-built/ported COs to a full Source→SO→Canonical→CO admit+resolve+eval plane for its own synthetic data. Concretely:

1. SO SUBSTRATE + INGRESS. The demo plane gains its own SO fact substrate demo.so_* (tenant-identical SO fact shapes; immutable/versioned; nullable source-family columns per the post-#959 ddl-generator), entering ONLY through 0047's DB-enforced synthetic-only ingress ORDER: load → fn_check_so_batch → fn_promote_so_batch, where bc_demo_loader writes ONLY demo_staging.* (the staging area bc_demo_runtime cannot read), fn_check_so_batch runs the customer-lineage rejection check plus admit-once/shape checks and FAILS CLOSED before any row is runtime-SELECT-able, and fn_promote_so_batch performs the atomic, content-digest-reconciled, visibility-gated promotion into demo.so_* — the exact 0049/0050 CO-write-path pattern, extended to the SO family. bc_demo_runtime keeps SELECT-only on demo.* and owns nothing (DEC-89db41 isolation contract unchanged). The D3 customer-lineage check is PROVENANCE-VERIFIED, not label-trusted: it does not accept a loader-supplied synthetic-origin label on its own (that would let a reader pointed at customer data label its rows synthetic and pass); it resolves the batch's actual admission-run/connection provenance against an immutable, owner-declared Foundry world/version→connection binding (the trust root bc_demo_loader cannot write), refuses when provenance is absent, mixed, or stale, and binds the promoted row set and its digest to the accepted (world, version) — so a source read becomes ONE governed immutable admitted version, not an unbounded incremental feed.

The trust root is the immutable source CONFIGURATION, not a mutable connection id. A connection id alone is insufficient: ConnectionRepository.updateConnection can repoint endpoint_uri + authentication_json under the SAME id, so an allowlisted id can be aimed at a customer source without changing the id. Therefore demo.foundry_world_binding binds (world_code, world_version) → connection_id AND a source-config attestation = sha256 over the canonical form of (endpoint_uri, credential identity — the secret's name/ARN/fingerprint, NEVER the secret bytes, source system, database/db name). The attestation is verified at BOTH gates: at FETCH, the reader refuses before any read if the live connection's config digest ≠ the bound attestation; at PROMOTION, fn_check_so_batch re-verifies the batch's recorded attestation against the binding and refuses drift / absent / mixed / stale. Repointing the connection under the same id therefore fails closed at the next read; a new world version is a new append-only, owner-declared binding row. The binding table and its owner declare-function fn_declare_foundry_world_binding are bc-db DDL (0054); the concrete v3_lc5 row (real connection_id + computed attestation) is declared at U5 via that function under U5's batch grant (the attestation is computed from the live connection and must exist before the fetch-time check); bc_demo_loader / bc_demo_runtime have no write.

The reader's connection authorization is PLANE-OWNED, not tenant-owned. The tenant-only assertConnectionOwnedByTenant is generalized to assertConnectionOwnedByPlane(plane, connectionId): a tenant plane keeps today's tenant rule byte-identical; a demo plane requires the connection to be declared demo-plane-owned in the immutable owner-declared trust root (demo.foundry_world_binding) and refuses anything else by name — never the tenant-owned connection (that would reintroduce a tenant, D1), never an unowned one (that would open cross-source reach). No other plane kinds.

2. ONE ENGINE, PLANE-PARAMETRIC — NO SECOND RESOLVE PATH. The admission write-path (today hard-wired to TENANT_DATA_DB in admission-batch.service.ts and reader-runtime/tenant-admission-run.service.ts) and the canonical resolver (today tenant-plane-ONLY — ccv2-canonical-resolver.service.ts:479-481 throws PlaneMismatchError "canonical resolution runs on the tenant plane only … (DEC-3f6b1b)", hard-coding tenantPlane()) are generalized to the declared RuntimePlane, so for RuntimePlane{demo} the SAME admission and the SAME resolver write the demo plane (the SO ingress for admit; demo.co_* for resolve), reusing the single engine. A demo-specific admit/resolve path is PROHIBITED (source-agnosticism, TSK-e42e87): source representation is normalized at the reader/observation boundary or declared in contracts, never with a source literal in the shared writer/resolver/evaluator; the typed-fact-writer.ts projectPayload source-representation coercions (SAP ''→null; Odoo false→null, many2one array→[0]) are relocated to a declared observation-normalization layer at the reader/ingress boundary so the shared writer stays source-literal-free (the repair, not an interim — leaving them in the writer as a G2-interim path is excluded).

The native CO write is a SEPARATE GUARDED PRODUCER, so the one engine does not need an unrestricted owner handle and bc_demo_runtime stays SELECT-only. Because the demo plane's runtime principal is read-only and the CO-fixture insert guard admits only the fixture promote function, the resolver's RuntimePlane{demo} CO write goes through a narrowly authorized producer — a dedicated principal that owns nothing and writes ONLY demo.co_* plus that CO's own same-plane canonical_evaluation and evidence/lineage, via a sole-writer promote function (atomic fact+evidence commit, digest-reconciled, the CO-fixture guard's allowlist extended shrink-only to admit it), with NO re-run of the external-lineage check (there is no new external data at the CO step — the D3 gate is at the SO ingress; the CO is a transitive derivation of already-gated demo.so_*). The single grouping/derivation engine selects this producer PORT for the demo plane and keeps the tenant transaction for the tenant plane — one engine, two declared producer ports; it is NOT handed an owner handle to the demo schema.

3. DECLARED LE BINDING. The demo chain's legal entity comes from the declared resolve_source_entity_binding derivation (D574/DEC-c05551, resolvedLegalEntity — a concrete code resolved against demo.dim_legal_entity), NEVER the SAP bukrs route (bounded and closed for non-SAP sources under DEC-ea4523) and never a '*'/blank identity (D623).

Because there is no tenant, there is no tenant provisioning fan-out and no global-activation readiness gate for the demo proof.

5. RELATIONSHIP. This EXTENDS DEC-3f6b1b (its plane-scoped CC-version binding and its "a plane proof never depends on or triggers a global activation" guarantee are UNCHANGED and remain decided; no supersedes_ref) and REALIZES DEC-89db41's plane generalization for the admit/resolve path. ## Addendum — observation membership on the demo plane is SC-level (TSK-084688, follow-on design act)

STATUS REMAINS proposed. This addendum is part of the decided-text the recorded grant carries; it records a follow-on design act (DEC-c48b0f) settled during the G2 end-to-end rehearsal and refines decision point 2 (one engine, plane-parametric) and the U3d absent-leg-mode ruling. It changes no earlier text.

CONTEXT. The rehearsal (scratch, no live act) resolved the sealed SO version through the one engine and matched the LC5 oracle to the cent with zero per-metric edits — confirming the plane-parametric admit→resolve. It surfaced one defect: a Canonical Contract with multiple legs over the SAME source contract pinned to DIFFERENT observation contracts (das36's primary leg under one OC, its currency leg under another) resolved currency_code NULL, because the demo plane's absent-leg mode gave each admitted row exactly ONE observation-contract membership (the primary), so the currency leg saw zero rows.

DECLARATION. On the demo plane, "observed as" is an SC-LEVEL BINDING fact, not a per-admission event: an observation contract version observes a SOURCE CONTRACT version, so every admitted row of a (source contract, version) is observed by EVERY observation-contract version bound to that (source contract, version). A leg's source filter is leg SELECTION within the observed set, never admission membership. This is guaranteed complete on the demo plane by its admission model — one live governed batch per binding, admit-once, linear supersession — so no partial per-OC observation is possible; the resolve fails closed (halts) if that completeness is ever violated (more than one typed run context, or a partial batch). The tenant plane records per-row observed_as only because its admission is incremental and per-OC-run and can be partial (a row observed by one OC but not yet another); membership-by-binding is the shared semantic truth on both planes, and the tenant's per-OC runs are completeness provenance for the incremental case, not a different definition of membership.

CONSEQUENCE (repair location C/D, resolver only; no admission change, no schema change, no bc-db migration). Demo-plane leg membership is computed by the one engine from IMMUTABLE, PINNED declarations: a row is in a leg iff (1) the leg's observation-contract version is referenced by the pinned Canonical Contract version being resolved, AND (2) that observation-contract version is declared to observe the admission's (source contract, version) — read from the immutable observation-contract version, never from live registry — AND (3) the row passes the leg's declared source filter (a filter miss is leg selection, not an out-of-contract membership error). Because every input is immutable and pinned, re-resolving yields identical membership (Invariant V, non-replayable/stable), meaning is evaluated once (Invariant I), references are explicit (Invariant IV), and the CO's own evidence (evidence hash + lineage, which reference the pinned Canonical Contract and the admission) emits the proof from which membership follows (Invariant VI — emitted, not inferred). Recording a per-OC membership set at admission was rejected: it would denormalize a binding fact already declared once at observation-contract authoring (one source of truth, DEC-1918d0 #4) and add sealed structure for a deterministic consequence of immutable declarations. The demo admission therefore records nothing new under this ruling.

## Addendum — the demo admission fetches the SC's declared OBSERVED field set (fetch-side twin, TSK-084688 follow-on design act)

STATUS REMAINS proposed. Part of the decided-text the recorded grant carries; a follow-on design act (DEC-c48b0f), the admission-side twin of the SC-level-observation addendum above, settled on Platform's read-only file:line trace during the rehearsal. It changes no earlier text.

CONTEXT. With the cohort rule in place the currency leg resolved the primary's rows, but currency_code was still NULL: the admitted Source Objects carried currency_id NULL on both entities while amount_residual_currency was populated. The trace located the drop at the FETCH LIST — `src/boundary/reader-runtime/resolved-admission-context.ts` deriveFetchFields builds the source fetch list from the ADMITTING observation contract's so_schema (∪ identity ∪ timestamp ∪ filter), and the executor reads exactly that list. The demo admitting OCs (account.move and account.move.line) do not declare currency_id in their so_schema, so the field is never fetched and never enters the raw row; the currency leg's OC (a sibling bound to the same source contract) needs it. The source has it (a direct read returns the many2one), the tenant kept it only because its admitting OC happened to select it, and U2b normalization is proven correct on both planes (it maps a present many2one to its id; an absent key stays absent) — so this is a FETCH-selection gap, not normalization and not an Odoo default.

DECLARATION. On the demo plane, the ONE governed admission of a (source contract, version) SHALL fetch the UNION of the so_schema selections of the observation-contract versions that the plane-pinned Canonical Contract's observation_references name for the leg's (entity, source contract, version) ∪ identity ∪ timestamp ∪ filter fields — not the admitting OC's selection alone, and not the source contract's full observed set. Reading the plane-pinned CC's observation_references at admission is a registry-DECLARATION read (the contract), not a canonical-OBJECT back-reference, so step one of the fixed progression takes no back-reference. This is the fetch-side consequence of the SC-level-observation rule: a row admitted once must carry every field any bound leg of the pinned CC will resolve, and the union is exactly that set; it is declaration-grounded and immutable (the pinned CC version names immutable OC versions). A source field no pinned OC selects is never fetched — so a field the source cannot actually serve (a Json/Binary/Html computed widget mis-declared observable, e.g. account.move.needed_terms) never enters the fetch and forces no SC change as long as no OC selects it; its mis-declaration is a tolerated, disclosed debt (DESIGN ACT A below). The reader refuses BY NAME on an inactive CC/OC version, an undeclared field, an empty kept set, or a source that omits a fetched field's key (the absent-key belt) — never a silent NULL or a partial read. The tenant plane's per-OC fetch is byte-identical.

CONSEQUENCE (repair location A, the admission fetch; no schema change, no bc-db migration, no evaluator change). deriveFetchFields becomes plane-parametric at the seam where the plane is already resolved (reader-runtime.service.ts): the demo plane derives the fetch list as the union of the plane-pinned Canonical Contract's OC-version so_schema selections ∪ identity/timestamp/filter, bounded by the SC's declared observed set (a bound OC naming a field outside it refuses by name — no column on the SC-level store); the tenant plane keeps its per-observation-contract so_schema list BYTE-IDENTICAL (its admission is incremental and per-OC-run, so each run legitimately fetches only its own OC's selection). The derivation stays fail-closed, and it is bounded by the declaration: a field the source contract does NOT declare is still never fetched. The 0054 Source-Object twins already carry a column for every observed field, so no schema change is needed; the demo Source Objects must be RE-ADMITTED under the new fetch rule (a new run/batch/version — the superseded admission remains immutable evidence, Invariant III). Widening the admitting OC's so_schema to carry the sibling's field (the alternative) was rejected: it distorts that OC's declared observation with a field it does not own, fixes the instance not the class, and would require re-authoring/re-certifying the OC. No formula is tied to fact shape and nothing is compensated below the fetch: the repair is where the field is dropped. Invariants: I (the SC declaration is the observable surface, evaluated once at admission), IV (the fetch set is the pinned CC's OC-version selections, bounded by the SC's declared observed set), VI (the Source Object carries what the admission observed, emitted not inferred).

VECTOR. After re-admission: every source-contract-declared field is populated on the staged Source Objects wherever Odoo carries it (currency_id non-NULL on both entities); the currency leg resolves currency_code; the per-currency oracle cells (e.g. USD and INR) match to the cent and SUM(outstanding_amount) stays oracle-exact; the tenant per-OC fetch path is unchanged byte-for-byte; and a field the source contract does not declare is still never fetched.
