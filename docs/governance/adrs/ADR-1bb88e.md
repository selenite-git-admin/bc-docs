# The demo plane is a RESOLVING plane — plane-parametric admit+resolve for its own synthetic data (G2, under DEC-89db41 D1/D3)

## Context

AUTHORITY (no reversal, no new direction — the PLANNED G1→G2): DEC-89db41 D1 (the metric-catalog drive stalled because "every recurring blocker was a tenant-plane crossing"; Demoed requires an end-to-end proof that lives in ONE plane and never crosses into a tenant; Option B / any tenant-shaped demo is REJECTED — "it reintroduces the tenant hinge the design removes") + D3 (synthetic-only owner-plane ingress; no-customer-lineage provable 3 ways: no direct privilege path, no indirect owner-rights path, synthetic-only governed contents). G0 §6 (accepted): the first proof enters at the CO level with authored-typed fixtures DELIBERATELY — "if instead the demo fixture were loaded through a source reader, [TSK-e42e87] point #1 would re-enter — so author typed, don't replay a source" — and names the next brick as the source/reader/admission binding. G1 §5: "the source→canonical admission is a distinct mechanism, provable separately later." APPROACH-dso-at-demoed-2026-10-27 §4 sequences G2 = "demo source/reader/admission binding under RuntimePlane=demo" (Codex platform-lane), after G1 substrate (0047-0052) and the G3/G4 fixture proof. So this ADR realizes the planned G2; it is not a reversal of fixture-first (which was the entry) and not a new direction.

WHY THIS IS CLEANER (not a regression): a demo-plane-native resolve emits each CO by the mechanism ON the demo plane, so the transport seam of any tenant-resolve-then-port route disappears (no export/relocate, no evidence-id carry) — Inv VI is satisfied natively. The alternative (a resolving demo TENANT) was examined and rejected: it reintroduces the tenant hinge D1 removes, and brings the tenant onboarding/activation/suspension lifecycle (a standing posture change) for no benefit the demo plane needs.

FOUNDATION (DEC-79b62f): Design/declaration act (DEC-c48b0f) — it declares the demo plane's admit/resolve capability + ingress contract, not a detector. Repair B (declare the second plane's admit/resolve semantics + the synthetic ingress) + C (bind the reader + the plane-parametric engine). Invariants: I (meaning produced once at the canonical boundary, now on the demo plane), III (immutable versioned demo facts), IV (explicit plane + declared LE binding, no '*' fallback), VI (COs mechanism-emitted natively with their own evidence), and the source-agnosticism constraint (TSK-e42e87: one engine, no source literal in the shared writer/resolver). No lower-layer compensation and no override: the demo COs are produced by the mechanism, not fabricated.

GROUNDING (bc-core origin/main): the seam = admission-batch.service.ts (TENANT_DATA_DB inject) + reader-runtime/tenant-admission-run.service.ts + ccv2-canonical-resolver.service.ts:479-481 (tenant-plane-only refusal) and :2028-2087 (resolvedLegalEntity/bukrs binding, DEC-ea4523); the ingress pattern = bc-db 0047-0050 (demo_staging load → fn_check → fn_promote); factSchemaOfPlane (demo schema holds co_/ms_ today, "there is no demo_fact"). ## Decision

Under DEC-89db41 D1 (Demoed is proven end-to-end in ONE in-platform demo plane, never crossing into a tenant) and D3 (demo.* holds only the platform's own declared synthetic demo data, entering through an owner-plane synthetic-only ingress whose customer-lineage check gates visibility, fail-closed), the demo runtime plane (schema demo.* inside bc_platform_dev, RuntimePlane{kind:'demo'}) SHALL be a RESOLVING plane — generalized from today's CO+MS EVAL plane over pre-built/ported COs to a full Source→SO→Canonical→CO admit+resolve+eval plane for its own synthetic data. Concretely:

1. SO SUBSTRATE + INGRESS. The demo plane gains its own SO fact substrate demo.so_* (tenant-identical SO fact shapes; immutable/versioned; nullable source-family columns per the post-#959 ddl-generator), entering ONLY through 0047's DB-enforced synthetic-only ingress ORDER: load → fn_check_so_batch → fn_promote_so_batch, where bc_demo_loader writes ONLY demo_staging.* (the staging area bc_demo_runtime cannot read), fn_check_so_batch runs the customer-lineage rejection check (proving the rows derive only from declared synthetic demo data, D3) plus admit-once/shape checks and FAILS CLOSED before any row is runtime-SELECT-able, and fn_promote_so_batch performs the atomic, content-digest-reconciled, visibility-gated promotion into demo.so_* — the exact 0049/0050 CO-write-path pattern, extended to the SO family. bc_demo_runtime keeps SELECT-only on demo.* and owns nothing (DEC-89db41 isolation contract unchanged).

2. ONE ENGINE, PLANE-PARAMETRIC — NO SECOND RESOLVE PATH. The admission write-path (today hard-wired to TENANT_DATA_DB in admission-batch.service.ts and reader-runtime/tenant-admission-run.service.ts) and the canonical resolver (today tenant-plane-ONLY — ccv2-canonical-resolver.service.ts:479-481 throws PlaneMismatchError "canonical resolution runs on the tenant plane only … (DEC-3f6b1b)", hard-coding tenantPlane()) are generalized to the declared RuntimePlane, so for RuntimePlane{demo} the SAME admission and the SAME resolver write the demo plane (the SO ingress for admit; demo.co_* for resolve), reusing the single engine. A demo-specific admit/resolve path is PROHIBITED (source-agnosticism, TSK-e42e87): source representation is normalized at the reader/observation boundary or declared in contracts, never with a source literal in the shared writer/resolver/evaluator; the typed-fact-writer.ts projectPayload source-representation coercions (SAP ''→null; Odoo false→null, many2one array→[0]) are relocated to a declared observation-normalization layer at the reader/ingress boundary so the shared writer stays source-literal-free.

3. DECLARED LE BINDING. The demo chain's legal entity comes from the declared resolve_source_entity_binding derivation (D574/DEC-c05551, resolvedLegalEntity — a concrete code resolved against demo.dim_legal_entity), NEVER the SAP bukrs route (bounded and closed for non-SAP sources under DEC-ea4523) and never a '*'/blank identity (D623).

4. GOVERNANCE RE-HOMED, NOT DROPPED. admit-once, provisioning-readiness (the owner schema-provisioner provisions demo.so_*/demo.co_*), the fail-closed customer-lineage check, and immutability (Inv III, new-versioned not ALTER) are enforced ON the demo plane. Because there is no tenant, there is no tenant provisioning fan-out and no global-activation readiness gate for the demo proof.

5. RELATIONSHIP. This EXTENDS DEC-3f6b1b (its plane-scoped CC-version binding and its "a plane proof never depends on or triggers a global activation" guarantee are UNCHANGED and remain decided; no supersedes_ref) and REALIZES DEC-89db41's plane generalization for the admit/resolve path. It supersedes ONLY the interim stance that "a non-tenant plane's COs are loaded pre-built, never resolved here" (resolver :479-481) — that was G1's first-proof ENTRY (G0 §6, authored typed fixtures deliberately), and this is its planned G2 successor. The Foundry demo world (v3_lc5) is the platform's own declared synthetic demo data (D3), read by the governed reader through the ingress gate.
