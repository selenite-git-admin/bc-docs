# Standing Claude↔Codex exchange family gen- (thread-addressed, permanent)

## Context

On 2026-09-25 BareCount development moved to the Mac Mini. Codex, the independent auditor, stays on the Windows laptop.
- **Long programs** already run on automated exchange families (d597, d617, d619, dbr, rte…). They are committed to bc-external-audit and Codex polls them.
- **Everything else** was relayed by the operator by hand: small design questions, one-off reviews and the shared PR-landing thread. That no longer works across two machines.

Several sessions take part on each side at once: many Claude sessions on the Mac, and many Codex threads on the laptop. So each message has to be addressed to a conversation. A family or a topic is not enough.

Not every piece of work has a DevHub task, so a task UID cannot be the address. The protocol cannot rely on a session remembering its own obligations either; this ADR was drafted in a session that had not yet opened a DevHub session. Addressing and sender identity are therefore enforced by the publisher, not left to discipline.

A fuller design is parked as TSK-861e27: a neutral ledger repo, a CI-rung notification "doorbell" and a builder/auditor roles registry. This decision is its first, minimal step and does not pre-empt it.

## Decision

1. **One permanent family, `gen-`.** It carries every Claude↔Codex item that no active program family owns: PR landing reviews, ADR/docs PRs, small design questions, one-off reviews, infra and DevHub items.
   - Program families are unchanged.
   - If a `gen-` thread grows into a program, the operator may move it to its own family.

2. **Every conversation is a thread.** A thread has an ID `gen-<6 hex>`, minted by the publisher when the conversation starts (`gen-publish.sh new-thread`) and checked to be unused.
   - Messages number per thread: `01` opens the thread.
   - File names carry both, so either side can route from the name alone, without opening the file:
     - Claude: `MSG-Claude-gen-<id>-<NN>-<slug>-<date>.md`
     - Codex: `RESPONSE-Codex-gen-<id>-<NN>-<slug>-<date>.md` (or `PROOF-`/`CLOSURE-Codex-gen-<id>-<NN>-*` for executor output), where `NN` is the number of the message it answers.

3. **Required headers** in the first 15 lines of every message and response:
   - `Thread:` the thread ID;
   - `From:` for Claude, `Claude SES-xxxxxx <project-slug>`; for Codex, its own thread name;
   - `Task:` `TSK-xxxxxx` or `none`;
   - `Topic:` the area: infra, docs, devhub, db, security, bc-core, bc-admin, bc-portal, bc-demo, bc-infra, or a new topic named in the message;
   - `Kind:` `landing` (approve or merge a PR at an exact head), `design` (review an approach before build) or `question`;
   - `Depth:` `light` or `full` (point 6).

   Each message and each response ends with exactly one final line: `NEXT: Claude | Codex | both hold`.

4. **The sender must have an open DevHub session.** Claude's publisher refuses a message unless the `From:` session exists in DevHub and is open. After publishing, it records the thread, number, commit and SHA-256 as a checkpoint on that session. A session that takes over the work later finds the thread there, through its session context.

5. **One open message per thread, closed only by a valid reply.** A message stays open until a **protocol-valid** Codex reply for the same thread and number is committed on `origin/main`. A reply is protocol-valid when:
   - its file name carries the same thread ID and number;
   - its first 15 lines hold all six headers of point 3, with `Thread:` equal to the thread ID;
   - it contains the exact raw SHA-256 (64 lowercase hex characters) of the committed message it answers;
   - it ends with exactly one final `NEXT:` line.

   A file name alone does not close a message. Claude's publisher refuses the thread's next number until such a reply exists. Closing a message this way is transport closure only: it is not acceptance, and it grants no authority, whatever the reply's disposition. Different threads are independent, and related items that are ready together are folded into one message.

6. **Depth follows consequence.**
   - `light`: docs, records, runbooks, notes, and small tooling with no platform behaviour.
   - `full`: database applies, schema, security, auth, cloud, secrets, and anything that changes platform behaviour or evidence.

   Codex may raise a message's depth, never lower it.

7. **Transport and routing.** Messages are files committed to `bc-external-audit` `docs/` on `origin/main`. A notify is only a hint: the receiver always re-fetches `origin/main` and reads the committed bytes.
   - **Codex side:** Codex's watcher, owned by Codex, detects new commits on `origin/main` whichever host published them. The recommended form is `git ls-remote` every 20–30 s, fetching only when the SHA changes, with the 5-minute heartbeat as the fallback. The watcher routes each `MSG-Claude-gen-<id>-*` file by thread ID: an unknown ID opens a new Codex thread, and a known ID goes to the Codex thread already holding it.
   - **Claude side:** a Claude session watches only its own threads. It fires on any new commit that is not a `MSG-Claude` commit, never on one file-name pattern.

8. **Authority comes only from the operator, directly.** A `gen-` message never carries authorization, and Codex never treats one as such. Merge authority, live DB applies, cloud changes and other operator-only gates are granted by the operator to Codex directly, per class or per item. By default Codex has no merge authority on `gen-`.

9. **The automation is permanent.** A thread close, a disposition or the words "over and out" do not end the family. The automation is torn down only on an instruction the operator gives Codex directly. The token `TEARDOWN-AUTOMATION` counts only when the operator gives it directly; a `gen-` message, or a token quoted in one, can never tear the family down (point 8).

10. **Custody.** Messages and replies are published byte for byte from a clean checkout of `origin/main`. The publisher checks the published file against the local file by SHA-256 and mirrors it locally. A reply binds its input by the raw SHA-256 of the committed message (point 5). Claude's publisher is `barecount-devhub/scripts/exchange/gen-publish.sh`; it relies on the reply check of point 5 only once that check has been implemented and reviewed.

## Consequences

- The operator no longer relays between the two models. On `gen-`, the operator's role is authorization only.
- The manual shared landing thread is retired for new items.
- Sessions on both sides share the family without reading each other's traffic, and a successor session can pick up a thread.
- Protocol compliance on Claude's side is a publisher gate, not a habit.
- Codex's watcher needs multi-family, thread-routed detection, which it lacks today (its current watcher is dbr-only). Codex builds and confirms that in the thread's first reply.
- The later ledger (TSK-861e27) imports `gen-` history as-is and keeps the header format.
