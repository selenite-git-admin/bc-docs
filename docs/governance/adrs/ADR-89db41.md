# Graceful D575 generalization to runtime planes {tenant, demo} — the in-platform demo runtime plane (bc_demo_runtime)

## Context

The metric-catalog drive stalled because every recurring blocker was a tenant-plane crossing; the Demoed terminal (DRAFT-ADR-demoed-platform-terminal-2026-10-26.md, D2/D2-guard/D3) requires an end-to-end proof that lives in ONE plane and never crosses into a tenant. D575 OWNS the runtime-plane model and its isolation, so the correct repair layer is to generalize D575 (not to compensate lower, and not Option B's separate DB). The demo plane shares bc_platform_dev with the platform definition schemas, so — unlike the tenant plane which gets isolation free from a separate database — its isolation must be an explicit DB-enforced grant/deny matrix plus the first-statement RT(demo) schema-reach gate, designed so the customer-data isolation is structural (not intent) and provable for a Codex isolation audit. Grounded in source (tenant-data.provider.ts, runtime-session-identity.ts RT gate, the three frozen d575-*.spec.ts). This DEC records ONLY the concrete, auditable plane generalization + isolation contract now; it REFERENCES the Demoed ADR draft, which stays a DRAFT and earns its own terminal-state DEC once DSO lands on the demo plane and proves it (no premature terminal-state scaffolding). ## Decision

Generalize D575's single hard-coded "tenant" runtime plane to a declared set RuntimePlane ∈ {tenant, demo}. The tenant plane is unchanged (bc_tenant_runtime, dedicated tbc_{slug} database, DB-isolated). The new demo plane is schema demo.* INSIDE bc_platform_dev (tenant-identical fact shapes, immutable/versioned), provisioned and OWNED by the owner-plane schema-provisioner, written/read ONLY by a new non-escalating, owns-nothing login bc_demo_runtime reached only via a request-scoped DEMO_DATA_DB provider (DEMO_DATABASE_URL), symmetric with TENANT_DATA_DB. Isolation is PRESERVED and generalized, not weakened. The isolation guard (DB-enforced, not app logic): bc_demo_runtime is NOT superuser/bypassrls/createrole/createdb/replication, is a member of no role, owns nothing; its grant/deny matrix gives USAGE+DML on demo.* ONLY, NO USAGE on any other bc_platform_dev schema (contract/mcf/concept_registry/progression/registry/infrastructure/tenant/tenant_dim/public), and NO CONNECT on any tbc_* tenant database. The first-statement identity gate RT is generalized to RT(demo): RT's clauses with the role parameterized PLUS a new schema-reach clause requiring the login's effective reachable schemas == {demo} exactly (accounting for the implicit, non-removable PUBLIC membership — default public-schema USAGE/CREATE to PUBLIC is revoked in the migration), with no fallback credential (DemoRuntimeCredentialAbsentError) and refusals NEVER_DEGRADED. The three frozen d575-*.spec.ts architecture gates generalize plane-parametrically, shrink-only (tenant assertions unchanged, demo assertions added). No-customer-lineage is provable two ways: no privilege path (no CONNECT to any tenant DB — Postgres has no cross-database query from one connection — and no USAGE on any customer-adjacent schema), and demo.* is synthetic-only by invariant (D3 of the Demoed ADR draft). Option B (a separate tenant-shaped demo DB) is rejected — it reintroduces the tenant hinge the design removes. Design act (DEC-c48b0f); Repair B (declare the second plane + isolation contract) + C (bind bc_demo_runtime). PROPOSED — operator ratifies via a recorded desk grant. Design-only: the execution (bc-db migration for schema demo + role bc_demo_runtime + the exact grants + catalog-postcondition checks, the DEMO_DATA_DB provider, the shrink-only spec generalization) is a SEPARATE operator-gated DBCP unit, not opened by the design act.
