# One contract-identity doctrine: UUID authority + opaque speakable uid, no semantic names, all families

## Context

The Odoo pilot exposed that the DEC-ea5074 SC name (sc__{system}__{table}) collides the moment a second Odoo edition/major arrives — ea5074 itself bet on "0 cross-version collisions today," which Odoo breaks. Fixing the token (odoo_ent_v19) only patches one family and re-opens the same granularity guess for the next system. Driven to root: names are not reference keys (references are UUIDs, Invariant IV), so a semantic name buys nothing but a parsing temptation; an opaque name plus a dropped display_name are just "two more UUIDs" (D162 Rule 4). D512 already proved the right shape for metrics — UUID authority + an opaque speakable label that is "a LABEL, never a reference." Maintaining D512 for metrics and a different scheme for the chain families is the same inconsistency one level up. So: one doctrine, D512 generalized to all six families, semantic names retired, meaning resolved from structure. This is the Invariant-IV-complete end state — it removes the standing temptation rather than relying on discipline not to parse — and it dissolves the naming-granularity problem permanently instead of re-deciding it per system. Decided now to lock the identity model before u5 authors the first Odoo SC/AC; implemented incrementally behind a name-reference audit because it touches the whole contract subsystem.

## Decision

One contract-identity doctrine for ALL contract families (Source, Admission, Observation, Canonical, Metric, Intervention). Two identifiers per contract, no more:

1. AUTHORITY — the existing UUID (`{family}_contract_id`, gen_random_uuid) is the SOLE identity and the ONLY reference key: every join, FK, lineage entry, binding, cc_field_mapping, metric_binding, tenant.contract_binding, package signature, cert closure, admission, gate, and find-or-create dedup resolves through it. No path may reference or resolve a contract by any human-facing string. (Affirms Invariant IV platform-wide.)

2. HUMAN HANDLE — one opaque, speakable, self-validating short UID per contract, generalizing DEC-195bbd/D512 from metrics to every family. Canonical form `{NS}-{payload}-{check}`: NS = mandatory family namespace (SC, AC, OC, CC, MC, IC); payload = Crockford base-32 (0123456789ABCDEFGHJKMNPQRSTVWXYZ, omits I L O U), EXACTLY 5 characters, stored bare, per-family UNIQUE — widens D512's 4-char metric payload to 5 because Source Contracts already number 30,377 and 4 chars gives only a ~90k comfortable ceiling per family, whereas 5 chars = 32^5 ~= 33.5M per family, ample for the highest-cardinality family at any realistic estate; check = one derived Crockford check symbol (value(payload) mod 37), NEVER stored (DB Rule 2), recomputed and verified on every parse, with the allocator redrawing any payload whose check falls in Crockford's extended symbols (* ~ $ = U). Namespace and check are DERIVED at display; only the payload is stored. ALLOCATION: random CSPRNG draw + clean-check redraw + unique-insert under bounded retry (N=8), assigned ONCE at contract creation in the same transaction as the contract row; ONE shared allocator + one format/parse helper pair serves all six families (differing only by namespace + the family's uid column). AUTHORITY BOUNDARY (retained from D512): the uid is a LABEL — never a reference, never an FK, never a fallback lookup authority; it MAY back an operator-facing convenience search (typed SC-A00BC-K -> validate check -> resolve to UUID) but no runtime/gate/signature/closure/admission/dedup path may resolve a contract by it or fall back to it when a UUID lookup fails.

3. NO DESCRIPTIVE NAME — the semantic `{family}_contract_name` slug (sc__{system}__{table}, cc__..., mc__...) and any human display_name are RETIRED as stored fields. They add no value once opaque (they duplicate the UUID — a D162 Rule-4 violation, "two more UUIDs") and, being parseable strings the machine never reads, exist only to tempt a human into deriving meaning by parsing them — the exact implicit-reference anti-pattern (Invariant IV) this doctrine removes. A contract's meaning is RESOLVED from its structured attributes (SC/AC: source_version -> system/flavor/version + object -> table; MC: grain/formula/unit) and shown as STRUCTURED columns in the UI, never a concatenated label.

4. DEDUP ON IDENTITY, NOT NAME — find-or-create keys on each family's identity tuple: SC/AC on (source_version_id, object, category); OC/CC/MC on their contract identity (e.g. MC one-per-KPI per D068). The name is never a uniqueness key.

SUPERSEDES DEC-ea5074 (SC/AC sc__{system}__{table} naming — whose own text concedes "the sourceObjectId UUID is the real identity; the name is a slug" and bet on "0 cross-version collisions today," a bet Odoo editions/majors break) and DEC-195bbd/D512 (metric_uid — absorbed and generalized to all families; nothing of D512 is implemented yet, so no code is lost). Any per-family OC/CC/MC naming convention is subsumed.

FOUNDATION GATE — repair location E (storage/projection: an immutable identity attribute on each contract row) + allocator in D (the contract writer). Why E/D: an opaque display identity of contract identity belongs on the contract row, minted at insert. Why not A/B: the uid carries no measurement meaning and declares nothing in contract grammar. Invariants: I n/a (opaque); II SATISFIED (random -> no catalog order/size leak, unlike a serial); III SATISFIED (write-once, never reused, never re-points after archival); IV SATISFIED (label only, never an FK; UUID is the sole reference — and retiring semantic names REMOVES the standing IV temptation); V n/a; VI SATISFIED (uid stored at mint, not inferred). No invariant violated; the doctrine strengthens IV.

IMPLEMENTATION (incremental, each phase its own DBCP/PR + review; decided now, applied over time like D512): P0 NAME-REFERENCE AUDIT (gating) — enumerate every place a contract is referenced or looked up by name across all families; confirmed so far: registerSourceStack dedups by name (WHERE source_contract_name=...). Audit cc_field_mapping, metric_binding, tenant.contract_binding, the canonical-resolution runtime, OC/CC/MC body cross-references, and admin UI. Every name-based reference is an Invariant-IV violation to convert to id/identity-tuple BEFORE any name column is dropped. P1 — add `{family}_contract_uid` (payload) column + per-family UNIQUE index + the shared allocator + format/parse helpers across all six families; new contracts born-assigned. P2 — re-key find-or-create to identity tuples. P3 — stop emitting semantic name/display_name for new contracts. P4 — backfill payloads to existing contracts (lock uniqueness incl. archived), then deprecate and drop the name/display_name columns (SAP's 30,377 SCs are retiring, so they age out cheaply). FIRST REALIZATION (u5, now): the Odoo account SC/AC are authored with UUID identity + an SC-/AC- payload uid, NO semantic name, dedup on (source_version_id, object) — the doctrine's first exercise, ahead of the platform-wide backfill.

CONSEQUENCES: every contract has exactly two identifiers — the UUID (sole authority) and one opaque speakable self-validating handle (SC-A00BC-K) — and zero parseable semantic names. One allocator, one format, one doctrine across all families (no metric-vs-rest split). Meaning comes only from explicit structured resolution, so no code can derive a contract's system/table/kind by string-parsing. The change is platform-wide (30k+ rows, the chain, the admin UI) and lands incrementally behind the P0 audit; u5 realizes it first for Odoo.
