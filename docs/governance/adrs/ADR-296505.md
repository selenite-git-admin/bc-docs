# Contamination expunge: whitelist-failing catalog rows get a governed delete path (not archive-forever)

## Context

The lifecycle had NO exit for admission errors. D557 pt 4 forces every approved/verified row to archive-never-delete; D562 declared non-table objects "contamination" but gave that category no removal path. Result: contamination admitted before a whitelist existed is stuck as a permanent tombstone — "we store garbage forever" (operator, 2026-08-09). The delete guard could not tell "retire legitimate history" from "expunge an admission error" and mechanically bucketed both as archive-only.

Invariant analysis (the crux): D557 pt 4 is the operational form of Invariant III — no historical rewrite — and it PROTECTS LEGITIMATE ADMITTED STATE. A contamination row is not a legitimate observation of the source; by D562 it is an entry the source-object boundary (A) should have REFUSED. Deleting it is therefore CORRECTING AN INVALID ADMISSION, not rewriting a true past. Invariant III protects legitimate observations, not admission errors; Invariant VI is honored by EMITTING expunge evidence (the expunge_log + the retained admission artefact/manifest), so the error and its correction stay auditable — we remove the invalid entry, not the proof it happened.

Why a guard carve-out and not a hack: disabling/dropping the delete trigger to force a delete is an execution-plane workaround for a design-plane gap (D541) and is not reusable. Making the guard data-driven on the row's own authoritative kind is declarative, cannot be silently bypassed (no transaction flag to abuse), and gives every future source the same clean contamination exit with zero per-source code. Why correction-before-expunge: the predicate must read SOURCE TRUTH, not a mislabel; correcting object_type_code first also leaves the surviving real tables honestly labeled. Why evidence-emitting: without the expunge_log the delete would be an inference-driven silent removal — the exact Invariant VI failure the platform forbids. Extends DEC-88870a (D562, the contamination policy) and DEC-3078ce (D557, the admit/verify/approve lifecycle) by adding the missing expunge transition; narrows D557 pt 4 rather than reversing it.

## Decision

A source_object / source_field row whose AUTHORITATIVE object_type_code fails the D562 admissibility whitelist (object_type_code IS DISTINCT FROM 'table' — i.e. 'view' or NULL/non-object) MAY be DELETED (expunged) regardless of catalog_status/verification_status, provided the delete EMITS expunge evidence. This is a narrow carve-out to the D557 pt 4 archive-never-delete rule; legitimate rows (whitelist-passing, i.e. real source objects) are UNCHANGED — they still archive, never delete.

MECHANISM (three parts, all governed DB changes authorized via DBCP):
1. Amend the shared guard fn_source_catalog_delete_guard so that, BEFORE the existing registered/unverified check, it permits the delete when the row is contamination: for source_object, when OLD.object_type_code IS DISTINCT FROM 'table'; for source_field, when the PARENT object's object_type_code IS DISTINCT FROM 'table' (looked up by TG_TABLE_NAME branch). The default path (registered/unverified deletable; everything else refused → archive) is untouched for whitelist-passing rows.
2. A new evidence table source.catalog_expunge_log records every expunge: object/field identity, the authoritative object_type_code that condemned it, the source version, the original admission artefact/manifest reference, actor, and reason. The delete is only legitimate BECAUSE this evidence is emitted (Invariant VI). Nothing is silently removed.
3. Expunge is only meaningful once object_type_code holds the AUTHORITATIVE kind. Where a prior admission mislabeled kinds (the Odoo A-gap: every model stamped 'table'), the object_type_code must first be CORRECTED to source truth (from the extractor's authoritative classification) before the carve-out predicate applies. Correction is a metadata UPDATE (object_type_code has no guard); it makes the catalog honest for survivors AND exposes contamination for expunge.

SCOPE: this is the general capability (every source admits some contamination before its whitelist catches everything — it is recurring, not an Odoo one-off). It does NOT authorize deleting whitelist-passing rows, and it does NOT touch contract rows (SC/AC); expunge targets only catalog objects/fields with no valid contract dependency (contamination never has SC/AC by construction). Child evidence (source_field_typing, source_field_derivation) is deleted with its field by FK order; that evidence described a row that should never have existed, and the expunge_log preserves the fact of removal.
