# RDS-portable canonical baseline — the versioned spine applies under a non-superuser cloud principal

## Context

The DB foundation is realized on managed RDS PostgreSQL by applying the same versioned spine as a deployment stage (DEC-c40e7a), and portability of roles and privileges to a managed or customer-supplied PostgreSQL is a stated requirement to be *evaluated, not assumed* (NFR-4).

When the cloud schema-apply was first exercised on a live managed instance, it failed at the very first statement of the canonical baseline. The baseline — generated from the sealed capture of the local development cluster — created the owning role as a full cluster superuser:

```sql
CREATE ROLE barecount LOGIN SUPERUSER CREATEDB CREATEROLE REPLICATION BYPASSRLS;
```

and set the ownership of every schema object to that role. Managed RDS PostgreSQL grants the customer **no superuser**: the master role is a member of `rds_superuser`, which cannot create a role carrying `SUPERUSER`/`REPLICATION`/`BYPASSRLS`, and cannot assign object ownership to a role it is not a member of. The baseline was therefore not applicable on RDS at all — a foundation blocker for cloud realization, discovered only by a live apply (static synthesis and the local from-zero equivalence gate, which runs as a superuser, could not surface it).

The baseline is applied *byte-identically and digest-bound* by design, so no apply-time adaptation is legitimate: the baseline itself had to become portable.

## Decision

The baseline **generator** is given a bounded, fail-closed portability policy so that one canonical baseline applies both locally and on RDS and reproduces the identical schema parity. The sealed capture is unchanged; only the generator's rendering policy changes, recorded in a machine-readable exclusion contract alongside the baseline.

1. **Administrative role attributes are an environment-bootstrap concern, excluded from the baseline subject.** `SUPERUSER`, `REPLICATION`, `BYPASSRLS`, `CREATEDB` and `CREATEROLE` are dropped from every emitted role; the owning role is rendered `CREATE ROLE barecount LOGIN;`. The runtime application connects as this role (a plain owner + login), which needs none of those attributes; migrations are applied by the bootstrap principal, not by the owner role. The exclusion is bounded, never silent: each attribute observed in the capture is recorded per role in the exclusion contract. A given environment may still grant the role superuser out of band; the baseline neither asserts nor requires it.

2. **A temporary, guarded, revoked ownership bridge** lets a non-superuser bootstrap principal assign object ownership to the owning role. It grants the applier the minimal proven-sufficient membership immediately before the ownership layer and revokes it immediately after, is guarded to no-op when the applier already *is* the owning role, and — because schemas must be owned before the objects they contain — transfers schema ownership first. Object ownership therefore lands on the owning role identically to a superuser build.

3. **Managed-extension creation, ownership and member objects are outside the baseline subject.** The extension is created by the bootstrap principal and its member objects are not asserted owned by the baseline's owning role; a managed extension hosted inside a declared managed schema fails closed.

4. **The residual creator-admin membership is characterized by an actor-conditioned, fail-closed rule.** PostgreSQL grants a role's *creator* an automatic admin membership that a non-superuser creator cannot self-revoke. After the bridge revokes, therefore: a **non-superuser** creator leaves exactly one bounded environment creator-admin edge (member = the environment bootstrap principal, a non-baseline role; `admin` only, no inherit/set); a **superuser** creator leaves zero such edge; in both cases no elevated bridge edge, no membership among baseline roles, and no other owner-role edge remain. This residual edge involves the environment bootstrap principal, not a baseline role, and is a bounded environment-bootstrap exclusion.

The successor baseline reproduces the **identical schema parity fingerprint** as the superseded baseline — administrative role attributes and the ownership bridge are outside the parity subject, and the applied schema structure and object ownership are unchanged. Both actor classes are proven on the pinned engine by disposable machine checks (a superuser build asserting zero residual edge; a non-superuser build asserting the exact one-edge shape, the fully-revoked bridge, and atomic rollback on an induced mid-apply failure). The successor is ratified at gate ③, superseding the prior baseline, which required a superuser and could not be applied on RDS.

## Consequences

- **The versioned spine is now genuinely RDS-applicable** — DEC-c40e7a's "same spine applied to RDS as a deployment stage" is achievable, and NFR-4's portability evaluation is satisfied for roles and privileges rather than assumed.
- **One baseline, two environments.** The identical baseline applies under a local superuser bootstrap and under the RDS `rds_superuser` master; parity is identical. Portability is by construction.
- **The owning role is a non-superuser LOGIN owner in the baseline subject.** Where a local environment historically ran that role as the bootstrap superuser, that remains an out-of-band environment fact outside the baseline subject; the live development database is re-adopted against the successor baseline by a provenance-only supersession record, with no schema change (the parity subject is unchanged).
- **The bounded exclusions are enforced fail-closed by the generator and the from-zero proofs**, so a future regeneration cannot silently drop a grant, mis-shape the residual membership, or host a managed extension where its members would fall into the subject.
- **No production action is implied.** Production cutover remains an operator-only gate; live cloud units carry their own accepted evidence, backup-first, at zero standing cost until an environment is deliberately provisioned.

This decision refines DEC-c40e7a and does not change the hosting decision (DEC-1918d0, RDS PostgreSQL) or the spine-as-change-mechanism model (DEC-b1a286).
