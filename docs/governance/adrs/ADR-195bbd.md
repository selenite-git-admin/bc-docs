# Human-readable 4-character metric UID for MCF metric contracts

> **Superseded by DEC-3fe389 (D560), 2026-08-08.** This decision's mechanism (UUID sole authority + an
> opaque, speakable, check-summed Crockford handle that is "a LABEL, never a reference") was correct and
> is retained — but generalized from metrics to ALL contract families under one doctrine, rather than
> kept as a metric-only scheme. The payload widens 4→5 Crockford chars platform-wide (source contracts
> already number 30,377). Nothing of D512 was implemented, so no code changes on supersession; new work
> follows D560. The metric handle becomes `MC-<5>-<check>` under the uniform rule.

## Context

The live MCF metric stack identifies metrics only by a raw gen_random_uuid() (`metric_contract_uid`) plus a long descriptive slug (`mc_name`); there is no short, speakable, transcription-safe handle for operators, docs, or UI. The legacy `metric.metric_definition.metric_seq → MT-{seq}` scheme is dead (0 rows) and, being a monotonic serial, would leak catalog size/order (Invariant II) — so it is not revived. A 4-char code over a 10-12k catalog has ample room (32^4 ≈ 1.05M, ~87x headroom) but a small enough space that random assignment collides (~69 expected collided pairs at 12k), mandating a UNIQUE + bounded-retry allocator. Crockford base-32 drops the four transcription-ambiguous letters (I L O U), which is exactly what a human-readable id needs. Keeping the UUID as the sole internal reference and treating `metric_uid` purely as a display label preserves Invariants III (immutable, no reuse) and IV (references stay explicit/UUID). Naming follows DEC-69f09e: an opaque per-row unique surrogate is a `_uid`, not a `_code` (which is reserved for controlled business vocabularies), so the column is `metric_uid`. No tenant scoping: MCF metric contracts are platform-scoped and authored once; tenant specificity lives in the binding layer.

## Decision

Introduce `metric_uid` — an opaque, immutable, globally-unique human-readable short UID — as the human-facing identifier of an MCF metric contract (`mcf.metric_contract`), alongside (never replacing) the `metric_contract_uid` UUID key and the descriptive `mc_name` slug.

AMENDMENT (2026-07-12, pre-implementation). This decision was refined before any code/DB change: the human UID gains a Crockford **check symbol** (derived, never stored) and a **mandatory display namespace** (`M-`), making the canonical human identity `M-<payload>-<check>` (e.g. `M-A00B-K`); a version-qualified conversational form `M-A00B-K/vN` is defined; and the authority boundary is strengthened — the human UID is a cross-checked *display* identity and is **never a fallback lookup authority**. The **stored** value is unchanged: the 4 bare Crockford payload characters only (the check symbol and namespace are derived at the display boundary, per DB Rule 2 — no derivable value is stored).

NAMING. Per DEC-69f09e (ISO 11179-5) the representation term `_uid` = "human-readable short UID" (as with `session_uid`, `member_uid`), and `_code` = "business code / controlled vocabulary" (as with `status_code`, `currency_code`). The value is an opaque unique surrogate, not an enumerated vocabulary, so the conforming term is `_uid`, not `_code`. `metric_code` is explicitly rejected.

FORMAT (payload — the stored value). Alphabet = Crockford base-32 `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (omits I L O U). Exactly 4 payload chars; column regex `^[0-9A-HJKMNP-TV-Z]{4}$`. Stored canonical uppercase; matched case-insensitively. The stored `metric_uid` value is the BARE 4 payload characters (e.g. `A00B`) — no embedded namespace, no check symbol (a deliberate departure from the prefixed `_uid` value convention of SES-/MDM-/TSK-). Capacity is set by the payload only: 32^4 = 1,048,576, reduced to ~907,000 by the clean-check-symbol allocation rule below (still ~75x the 10-12k target; comfortable operating ceiling ~90,000 at 10% fill). Adding the check symbol does NOT expand the address space — it is derived from the payload.

CHECK SYMBOL (derived — never stored). A single Crockford check symbol is computed from the 4-char payload as `value(payload) mod 37` per the Crockford base-32 checksum spec (prime modulus 37 catches every single-character error and every adjacent transposition). To keep the human identity within the clean 32-symbol alphabet, the allocator REDRAWS any payload whose check symbol would fall in Crockford's five extended check-only symbols (`* ~ $ = U`); thus the emitted check symbol is always a normal Crockford character. The check symbol is recomputed and verified whenever a human UID is parsed — it is NOT persisted (DB Rule 2: no stored derivable value).

DISPLAY & VERSION FORM. The canonical human identity is `M-<payload>-<check>` — namespace, payload, check, hyphen-separated (e.g. `M-A00B-K`). The `M-` namespace is MANDATORY in all human-facing surfaces (UI, docs, conversation) — it is not an optional cosmetic prefix. When a specific metric-contract *version* must be named in conversation or docs, the version-qualified form is `M-<payload>-<check>/vN` (e.g. `M-A00B-K/v3`), where `vN` is the MCV `version_code`. The `/vN` suffix is composed from the MCV at display time and is likewise never stored on the parent row.

ALLOCATION. Random (CSPRNG), not sequential — draw 4 payload chars, mapped into the 32-symbol alphabet; DISCARD-AND-REDRAW any payload whose Crockford check symbol falls in the extended set `* ~ $ = U` (so the emitted check stays a clean Crockford char); then insert the payload under a UNIQUE constraint. On unique-violation, retry with a fresh draw bounded to N=8 attempts (at 12k fill the per-draw collision rate is ~1.3% after the ~13.5% clean-check reduction, so 8 attempts fail with probability <1e-14). Mirrors the existing MDM-/DEC- allocator convention (random short id + unique index), NOT the retired legacy `metric_seq serial`. Assigned once, at metric-contract creation, inside `insertParentMc` (`mcf-cert-writer.service.ts`) in the same transaction as the `metric_contract` INSERT. Grain = per metric contract (per KPI), not per version: all MCVs under one MC share the parent's `metric_uid`; a genuinely new MC gets a new `metric_uid`.

AUTHORITY BOUNDARY. `metric_contract_uid` / `metric_contract_version_uid` (UUIDs) remain the SOLE authority for joins, package signatures, cert closures, admissions, and PE-MC gates — these paths accept UUIDs only and never a human UID. The human UID (`metric_uid` / `M-A00B-K`) is a cross-checked DISPLAY identity: it MAY back an operator-facing convenience lookup (a search box resolving a typed `M-A00B-K` to its UUID, after check-symbol validation), but it is NEVER a fallback lookup authority — no runtime, gate, signature, closure, or admission path may resolve a metric by human UID, and no code path may fall back to human-UID resolution when a UUID lookup fails. Cross-checked means: a hand-typed human UID is validated by its check symbol before any lookup, so a mistyped id is rejected rather than silently resolving to the wrong metric.

IMMUTABILITY & ROLE. `metric_uid` is a LABEL, never a reference — all internal joins, FKs, cert subjects, bindings, and fact-table names continue to key on `metric_contract_uid`; `metric_uid` is never used as a foreign key (Invariant IV). Once assigned it is never mutated and never reused, including after archival, so an old value never re-points (Invariant III).

FOUNDATION GATE. Repair location E (storage/projection) — an added immutable attribute on the identity-bearing MC row — with the allocator in D (metric-draft writer). Why this location: an opaque display identifier of MC identity belongs on `mcf.metric_contract`, minted at insert. Why not A/B: the uid carries no measurement meaning, declares nothing in contract grammar, touches no source, and MUST NOT live in MC/CC grammar. Why not lower: this is the lowest identity-storage layer for a metric. Invariant check: I n/a (opaque); II satisfied (random → no order leak, unlike a serial); III satisfied (write-once, no reuse); IV satisfied (label only, never an FK); V n/a; VI satisfied (uid stored at mint, not inferred). No invariant violated.

DBCP (requires explicit operator approval before execution — not yet applied). 1) `ALTER TABLE mcf.metric_contract ADD COLUMN metric_uid text` (18→19 cols, ≤20 per D162 Rule 6). 2) `CHECK (metric_uid ~ '^[0-9A-HJKMNP-TV-Z]{4}$')`; `CREATE UNIQUE INDEX uq_mcf_mc_metric_uid ON mcf.metric_contract(metric_uid)` (global unique — not partial — so archived values are never reissued); NOT NULL added only AFTER backfill. The DB CHECK constrains the stored PAYLOAD only (`^[0-9A-HJKMNP-TV-Z]{4}$`); the check symbol and `M-` namespace are NOT stored and NOT constrained at the column. 3) Add `allocateMetricUid(tx)` in `mcf-cert-writer.service.ts` (draw + clean-check redraw + unique-insert), called from `insertParentMc`, bounded-retry on unique-violation; plus a pure `formatMetricUid(payload)` / `parseMetricUid(human)` helper pair (compute + verify check symbol, strip/require `M-` namespace) used at every display and operator-lookup boundary. 4) One-time governed backfill assigns payloads to the 149 active MCs (and archived rows, to lock uniqueness) via the same allocator, then SET NOT NULL. 5) Expose BOTH the raw payload and the canonical display form (`M-A00B-K`) in `mcf-read.service`, chain-status/summary payloads, and metric-directory realized views (joins stay on `metric_contract_uid`; the human UID is display/convenience-lookup only, never a join key).

CONSEQUENCES. Every metric gains a short, speakable, SELF-VALIDATING id: docs/UI/conversation reference `M-A00B-K` (or `M-A00B-K/v3` for a version) instead of a UUID or long slug, and the check symbol rejects a mistyped id before it can resolve to the wrong metric. `metric_contract_uid` remains the sole internal reference key — no join/FK migration, and no authority path (signature/closure/admission/gate) ever accepts the human UID. A bounded-retry allocator + clean-check redraw + unique index are mandatory (4-char space → real birthday collisions: ~69 expected collided pairs across 12k without a uniqueness guard). Adds one column + one backfill; the check symbol and namespace are derived at the boundary, so nothing derivable is stored. No change to MCV, bindings, or fact tables.
