# Curated-content promotion through the spine (W3)

## Context

The platform database is the system of record for what the platform *knows*. Its schema is now reproducible and forward-only (W1), and small master-data reference rows are seeded through the spine (ADR-5eed17). But the platform's **most valuable content** — metric contracts and definitions, business concepts and the governed vocabulary, the metric directory, source catalogs, and the contract families — has **no versioned, digest-bound, promotable source**. The only copies are the live `bc_platform_dev` and stale raw `pg_dump` snapshots (committed `docker/redesign/golden-snapshot-*.sql` from months ago, and an S3 `golden-platform` dump), neither canonical, deterministic, nor digest-bound. `seed:registry` regenerates reference catalogs and contracts from repo JSON, but **it has never been proven that the live database equals what the seeds would produce**, and live panel-authoring diverges from that JSON.

Two facts, verified against `main`, anchor the design:

1. **Curated content is authored live; the database is the source of truth.** The governed authoring panels (`src/registry/bcf/panel/`, `RegistryAuthoringService`, the MCF metric-authoring path) write to the platform DB, and the genesis seeds explicitly cede authority to it once bootstrapped — e.g. the F4 vocabulary seed states the source of truth after bootstrap is `concept_registry.characteristic` and that changes go through governed authoring, **never** by editing the seed payload (DEC-02f5a9). So the versioned source for promotion must be **captured from the authoring database through the governed path**, not a hand-maintained JSON copy.
2. **There is no content export/version/promotion mechanism today.** bc-db capture tooling fingerprints the *catalog* (DDL) only; there is no row-content capture, no `content/` tree (greenfield), no published content version, and no cache keyed on one. Ad-hoc "promote" scripts elaborate KPIs within one DB; they do not move content between environments.

This wave delivers FR-12 (per-collection canonical/deterministic/digest-bound export, promotable by the same runner, CI parity per collection against an authorized immutable scoped capture with no live credentials), FR-13 (authoring UI stays the front door; promotion exports/reviews/commits what was authored), FR-8's parity for content, and the content-version half of FR-14/§8.7 (promotion publishes a version that keys caches).

## Decision

Curated content becomes a first-class **promotable data class on the same spine** as schema and seeds, with exactly one source of truth per collection: **the live authoring database.** The mechanism has five parts.

### 1. Collections and their single source of truth

W3 governs these curated-content **collections**, each with one authoritative platform-DB source; the exact table set per collection and the metric two-store resolution below are settled in the per-collection implementation units:

- **Metric content** — `mcf.metric_contract` (+ versions, variable/filter/computed-dimension bindings): the digest-bearing identity substrate and the **canonical metric content of record**. `metric.metric_definition` (+ `metric_knowledge`) is the catalog/knowledge layer linked by `mcf.metric_contract.metric_definition_id` (the single-SoT FK direction). The implementation unit decides whether these ship as one collection with two layers or two linked collections; `mcf` is the digest-bearing canonical export target.
- **Business concepts & governed vocabulary** — `concept_registry.*` (entities, business concepts, characteristics/representation-terms/aliases and their append-only versions/supersessions).
- **Metric directory** — `metric_directory.*` (family/group/member and decisions), authored live (no genesis seed).
- **Source catalogs** — `source.*` (the D019 provider→field hierarchy).
- **Contracts** — the `contract.*` families (source/admission/observation/canonical/metric/intervention/ai + lineage, `contract_uid`, meta-schemas, canonical_mapping).
- **Authored provenance/certification** — the live `bcf.certification_record` / `bcf.panel_output_record` and the MCF equivalents are carried **as evidence** attached to the content they certify (see part 4). The legacy `contract.*` mirrors of these tables are not the capture target.

**Seed JSON is demoted to genesis/reference only** (resolving the current one-SoT ambiguity): `seed:registry` remains the bootstrap generator, but for any collection W3 governs, the **database is authoritative** and the seed JSON is no longer treated as a parallel truth. Where a collection is still re-applied from JSON today (the contract families), the implementation unit repoints it so the DB is the source and the JSON is genesis-only.

### 2. Canonical export (per collection)

Each collection exports to a **canonical, deterministic, digest-bound, version-controlled artifact** in the bc-db versioned tree (`content/<collection>/…`): stable row and key ordering, normalized serialization, and exclusion of non-content volatile fields, so the **same DB state produces a byte-identical export**. Each export carries a per-collection content digest and contributes to an aggregate content digest. Small collections (vocabulary, metric directory, master) are single files; large ones (metric contracts and source catalogs — thousands of rows / >100 MB raw) are chunked deterministically. The export is produced by a governed capture from the authoring database (reusing the DEC-c99f72 capture-authority pattern — an authorized, immutable, scoped capture), never by hand-editing.

### 3. Promotion by the same runner

The **same forward-only runner** imports and applies content exports to a target environment in **two phases** (staging then activation — the atomicity and dependency contract is §6), recording each application in a **content ledger** (analogous to the migration ledger: content name + digest + review disposition, recorded in the same transaction as the apply), under the governed owner identity with advisory locking, and coordinated-excluded from the owner worker's dynamic path (FR-25). Promotion is forward-only and idempotent per collection+digest; per-collection promotion and retry are permitted, but **cannot activate a partial release** (§6). Content promotion is a distinct artifact class from DDL migrations and from `kind:seed` master-data seeds; whether it is carried as a new runner content-apply path or a new migration `kind` is an implementation decision.

### 4. Authoring boundary and provenance-without-new-trust (FR-13, FR-12)

Authoring stays the **front door**: content is created and certified only through the governed UI/panels writing to the DB. **Promotion is the export→review→commit step**, never an authoring path — content is never created by editing an export. Provenance and certification fields (created-by, `certification_record_id`, `panel_run_uid`, identity digests) travel **inside the export as evidence**, with their source identity and digests **re-verified through the governed path** on promotion. Carrying them **confers no new trust and cannot mint verified state**: a promoted row's certified/approved status is a faithful, digest-verified copy of what was authored upstream, not a fresh grant issued by the promotion.

### 5. Content version + parity gate

- **Content version + caches (FR-14/§8.7).** The **active release manifest** (§6) publishes a single content version (plus per-collection digests) that the application and owner worker read through the runtime schema/content contract (FR-23); platform read caches are **keyed on that active content version**, so an activation invalidates them and consumers only ever observe the active manifest's content. This is greenfield — no content version exists today.
- **Parity CI (FR-12, the load-bearing gate).** CI proves, **per collection**, that a fresh build's content (from the versioned export) equals an **authorized, immutable, scoped capture** of live content — with **no live credentials in ordinary CI** (FR-6). This is the content analog of the W1 from-zero schema-equivalence gate; it closes the standing gap ("never proven the live DB equals what the seeds would produce") and makes `build == dump == live` hold for curated content, not only schema and master data.

### 6. Release manifest, atomic activation, and dependency contract (the correctness boundary)

Collections are independently exportable and promotable, but a release is **activated atomically as one manifest** — never per collection — so a retry or outage can never expose a mixed release (one collection new, a linked one old) and the ledger can never diverge from the published version.

- **Immutable release manifest.** A release is an immutable manifest listing every collection in it with its exact content digest, an **aggregate content version**, and explicit **inter-collection dependency constraints** (which collections must be co-consistent — e.g. metric content depends on the contract families and source catalogs at compatible digests). The manifest is the unit of activation and of consumer-visible truth.
- **Staged then activated.** Phase 1 (staging): the runner applies each collection's content to the target and records it in the content ledger against a **pending** manifest; staged content is **not published** — the active manifest/version does not advance, and consumers keep reading the prior active manifest. Phase 2 (activation): **only after every required collection in the manifest has applied and the manifest validates** (all declared digests present, dependency constraints satisfied) does the runner **atomically flip the single active manifest/version pointer** to the new one. Activation is the only publish.
- **No partial activation; last-good retained.** A partial or unvalidated set **never activates**. On any failure before activation, the **prior active manifest/version is retained** unchanged (last-good), and consumers/caches continue to serve it. Per-collection retry stays within staging.
- **Consumers read only the active manifest.** Caches and the runtime content contract (FR-23) read only the active manifest's version/digests; staged-but-unactivated content is never served. The physical staging mechanism (version-scoped rows, a staging area, or a single activating transaction) is an implementation choice, but it must guarantee this no-mixed-release property.
- **Interruption recovery / idempotency.** Per-collection apply is idempotent on (collection, digest). An interrupted promotion leaves the prior active manifest live; re-running resumes staging the incomplete collections and activates only when the manifest is complete and validated. A staged collection whose bytes do not match its manifest digest fails closed; activation with any missing or mismatched required collection is refused.

## Alternatives considered

- **Keep raw `pg_dump` snapshots as the versioned source.** Rejected. They are neither canonical, deterministic, nor digest-bound; they diff noisily, can't prove per-collection parity, and already drift (the committed and S3 copies are months stale).
- **Treat `seed:registry` JSON as the source of truth and promote that.** Rejected. It violates FR-13 (authoring is live) and the established DB-as-SoT rule (DEC-02f5a9); the JSON already diverges from live panel edits. Seed JSON stays genesis-only.
- **Extend the master-data seed mechanism (ADR-5eed17) to carry curated content.** Rejected as the primary path. Seeds are tiny fixed reference rows declared *in source* with hand-written invariants; curated content is large, UI-authored, and its truth is the DB. Forcing authored catalogs into hand-declared seed migrations would re-introduce the hand-maintained-copy drift this wave removes. The boundary: **authored-in-DB → curated content (W3 promotion); fixed-declared-in-source → seed (ADR-5eed17).**
- **Author content by committing export files (git as the front door).** Rejected — violates FR-13; loses the panel/certification governance; promotion is not authoring.

## Not decided here

- The exact per-collection table sets, and the **metric two-store resolution** (`metric.metric_definition` vs `mcf.metric_contract` as the promotable content of record) — settled per collection in the implementation units, `mcf` as the digest-bearing canonical target.
- The canonical serialization format and deterministic chunking thresholds.
- Whether promotion is a new runner `kind: content` path or a separate content-apply verb.
- Open question 1 (per-collection **volatility** classification, and capturing UI-authored content into promotion **without a manual step**): the principle is deterministic governed capture from the authoring DB with no hand step; the per-collection volatility list is an implementation-unit output.
- The authorized-capture custody specifics for content (reuse the DEC-c99f72 pattern; details per unit).
- The **physical staging/activation mechanism** that guarantees the §6 no-mixed-release property (version-scoped rows vs a staging area vs a single activating transaction) — an implementation choice, but it must satisfy the manifest activation, dependency, and interruption-recovery invariants in §6.
- Anything requiring cloud budget or a live/production promotion (Gate-④).

## Consequences

1. **G2 (one source of truth per data class):** each curated collection has exactly one declared source — the live DB — with seed JSON demoted to genesis; the drift between JSON, snapshots, and live is closed by the parity gate.
2. **G4 (protect the platform's value):** curated content becomes reproducible, versioned, digest-bound, and promotable between environments with provenance preserved and re-verified, minting no new trust.
3. `build == dump == live` extends to curated content: a from-zero build's content equals the versioned export equals the authorized capture, proven per collection in CI.
4. The spine gains a content artifact class + content ledger + published content version; consumers gain a version to declare compatibility against and to key caches on.
5. Each collection lands as its own reviewed implementation unit (export + parity + promotion), smallest/most-stable first (vocabulary, metric directory), large chunked collections (metric contracts, source catalogs) later.
6. **Atomic activation, no mixed release:** a release activates as one validated immutable manifest with an inter-collection dependency contract; a retry or outage never publishes a partial release and never diverges the ledger from the active version — the prior manifest is retained until the whole release is complete, and an interrupted promotion recovers idempotently.
