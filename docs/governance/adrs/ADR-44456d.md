# Revive bc-external-audit as the auditor's home: exchange protocol and mailbox, auditor instructions, Mac auditor service (courier stays retired)

## Context

- **The quota problem (measured 2026-09-28, TSK-070654, laptop Codex logs).** The auditor's ChatGPT Pro weekly limit ran from 0% to 100% in about 25 hours.
  - One Codex Desktop conversation, running since 09-25, drove about 61% of that burn: 635 messages, 4,379 model calls, average context 162k tokens.
  - 509 of those messages were a 5-minute heartbeat. 351 of the heartbeats found no work, yet each re-read about 620k tokens, which is 31% of that chat's input.
  - Non-BareCount projects on the same account took about 38%.
- **Operator decisions of 2026-09-28:**
  - keep Codex as the auditor;
  - give it a dedicated subscription on the Mac;
  - optimise the audit itself (not pre-decide review depth);
  - the access model in decision point 5;
  - revive this repository.
- **Why it isn't retired in practice.** DEC-b7d74b and the 2026-08-01 shutdown plan retired this repository as courier and proving ground, but it remained the live exchange mailbox (DEC-081931 point 7, used daily).
- **Why the auditor's machinery can't live with the builder.** The auditor's instructions, heartbeat automation and GitHub App key live only in a local folder on the laptop. The protocol is enforced in code only by the builder's publisher, in the builder's repository. Putting the auditor's machinery or the protocol validator solely in barecount-devhub would place the auditor's rules under the builder's control.

## Decision

1. **New scope.** `selenite-git-admin/bc-external-audit` is revived as the auditor's home repository. It holds four things:
   - **(a) The exchange protocol,** as a written, versioned specification plus one validator. The spec covers message and reply headers, thread numbering, the hash-bound Answers line, dispositions, the `Kind: close` end-of-life message, and the message states (sent, picked up, answered, closed, stale).
     - The builder's publisher (barecount-devhub `scripts/exchange/`) and the auditor's receiver both run this validator, each pinned to a named commit and version of this repository.
     - The validator checks form only. Nothing it accepts, and no builder-supplied byte, becomes authority over the auditor's disposition.
   - **(b) The exchange mailbox,** unchanged: messages are files in `docs/` on `origin/main` (DEC-081931 point 7).
   - **(c) The auditor's standing instructions and skills** (`AGENTS.md`, `barecount-auditor-session`), versioned and reviewed instead of living only in a local Codex folder.
   - **(d) The Mac auditor service,** under the separate macOS account `bcauditor`. It has four parts:
     - a watcher that polls `origin/main` without calling a model;
     - one fresh Codex run per new message, replacing the long-lived chat and its 5-minute heartbeat;
     - deterministic custody pre-checks (point 3);
     - one run record per review (time, token use, disposition), which the DevHub Auditor panel reads.
2. **What these records are, and what is not revived.**
   - The `gen-` mailbox is an administrative review transport (DEC-081931), separate from the metric-audit lanes.
   - Run records, pre-check outputs and protocol acknowledgements are **operational records only**. They are never metric verdicts, admission evidence, or substitutes for an independent checker conclusion.
   - The metric-audit response lane stays retired (DEC-b7d74b): signed checker packets, response-feed chains, epochs, pickups and bootstrap-authority gates. The metric-audit request lane is untouched (GOV-ERR-003).
   - This is not DEC-b7d74b's resurrection condition, and the retired engine code is not reactivated.
   - The legacy `bc_audit_store` tool server is not recreated on the Mac. If a later metric or store unit needs it, that unit justifies a separately pinned, reviewed installation.
3. **Scripted custody inputs are leads, not facts.**
   - **What the pre-check may do.** It may detect remote changes, compute raw hashes, parse headers, compare thread and number, collect the sender's DevHub session state, compare mirrors, and read the PR head, CI and App attestation. It hands this to Codex as a lead, with its tool versions and the raw evidence.
   - **What Codex re-checks itself.** On every consequential review, Codex independently:
     - re-fetches `origin/main` and hashes the committed input bytes;
     - checks the introducing commit and that no prior same-number response exists;
     - reads the sender's open DevHub session and the mirrors;
     - where relevant, verifies the exact PR head, CI and reviews, and any direct operator authorization.
   - **Who decides.** The reviewer alone decides substance, depth, disposition and whether a gate is met.
   - **Automated `Kind: close` acknowledgements.** The receiver may acknowledge a close without a model call only after it independently verifies every DEC-081931 point 11 condition:
     - the message is not number 01;
     - it has a sole Answers line binding the previous protocol-valid reply and its raw SHA-256;
     - it has a non-empty Outcome and Left open;
     - its final line is `NEXT: Codex`;
     - it comes from the current owner or a verified closed-owner orphan handover;
     - no finding is unresolved.

     The acknowledgement is itself a hash-bound, committed and mirrored response. On any unknown state the thread stays open and the item goes to Codex.
4. **Ownership and change control of this repository.** There are two gates.
   - **Technical gate.** An auditor reviewer, separate from the PR's author (a separate Codex run or session), checks the diff, tests, CI, the App actor and its permissions. It records a disposition bound to the exact head.
   - **Terms gate.** The operator approves any change to the protocol spec and validator, the standing instructions, or the custody pre-checks.
   - **Merging.** The auditor App merges only after both gates.
   - **The builder** may propose changes by PR or exchange message but never merges auditor code.
   - **No substitutes.** No generic GitHub identity stands in for the auditor App for approval or merge.
5. **Access (operator-agreed 2026-09-28).**
   - **Reads and runs.** The auditor reads and runs everything the builder can: repositories, database read access, AWS read access, running services, tests.
   - **Writes.** It writes only to this repository, and approves or merges PRs only through `bc-auditor-app`. It has no database writes, no AWS changes, and no access to the builder's working folders.
   - **Installation scope.** Any change to the App's installation scope, including adding this repository, goes through the operator's change control. The same change updates the App's allowed-repository set (the least-privilege contract its capability attestation checks), and the capability attestation is re-run before the auditor relies on it.
6. **Preparation before new content lands.**
   - Tag the current `main` as `archive/pre-revival-2026-09-28`.
   - Close the stale open PRs, each with a stated reason.
   - Move or remove the retired engine code after the tag, recording which was done.
   - Rewrite the README to the new scope.
   - Preserve the laptop's local worktrees per the preservation steps of the 2026-08-01 shutdown plan before any deletion.
7. **The 2026-08-01 shutdown plan** (review packet, never authorized) is set aside as to the repository's fate: the remote stays active. Its local-worktree preservation steps remain the guide for the laptop cleanup.
8. **Cutover needs a separate direct operator grant.** The `gen-` family is permanent, and its teardown or re-routing is reserved to a direct operator instruction (DEC-081931).
   - **Shadow mode first.** The Mac service runs in shadow mode. It detects, pre-checks and runs Codex, but writes its would-be replies outside the mailbox and never commits to `docs/`. The laptop watcher stays the single writer.
   - **What the parallel run must measure:**
     - detection;
     - per-thread ordering;
     - response de-duplication;
     - close and finding behaviour;
     - crash recovery;
     - custody across the remote, the Windows mirror and both Mac mirrors;
     - delivery and hard-gate results as well as dispositions.
   - **The grant.** Only a separate, direct operator cutover grant switches the writer. Until then, this ADR does not authorize:
     - switching off the laptop watcher or heartbeat;
     - moving the live route;
     - deleting or moving an App key;
     - creating or changing an account.

     At the switch, exactly one writer is active: the laptop stops before the Mac starts committing.

## Why this option

- It keeps the transport unchanged, so no messages move.
- It gives the auditor's rules and service a reviewed, versioned home outside the builder's control.
- One shared validator makes the protocol the same code on both sides, without giving it authority over dispositions.
- It removes the two largest measured costs: idle heartbeats and ever-growing context.

## Alternatives rejected

- **A new exchange-only repository:** it would move the mailbox and change DEC-081931, the publisher and the receiver for no added benefit.
- **Auditor machinery in barecount-devhub:** builder ownership of auditor rules.
- **Leaving the laptop setup as is:** unversioned instructions, personal-credential commits, quota exhaustion.

## Consequences

- DEC-081931 and runbook section 10 stay valid for transport; the runbook is updated for where the auditor runs.
- The builder's publisher gains a pinned dependency on the shared validator.
- Follow-ups:
  - the DevHub Auditor panel;
  - a runbook update;
  - deleting the copied laptop logs (`~/codex-audit-logs`) after the service is proven;
  - the Postgres superuser password rotation.
