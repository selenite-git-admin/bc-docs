## 1. Governing decision — LE is a system/runtime axis on the opaque legal_entity_id; LE-bearing is a FIRST-CLASS GOVERNED FIELD (B1 + red-team B-2)
No contract — canonical or metric — declares the LE value or its derivation; `legal_entity_id` is resolved universally at runtime (§2) and stamped as a SYSTEM column. Whether an object is LE-bearing is an object-level CLASSIFICATION.
**B-2 fix — the discriminator must be a governed field, not an eyeball.** There is NO object-level posting-fact/reference-master classification today — only `concept_registry.business_concept.kind ∈ {value, reference}` (BCF field-level, not object-level); the object table that might once have carried it was RETIRED under D417/D418 (a CI guard fails the build on any textual mention of its name, so it cannot be the home and is not named here). The REAL object-level home is **`concept_registry.entity_version`** (the IMMUTABLE descriptive version — `src/database/schema/concept-registry/entity.ts`), **NOT** the `entity` anchor (whose `active_version_id` pointer changes). So "LE-bearing" becomes a **first-class GOVERNED CLASSIFICATION on `entity_version`** — a new governed column (e.g. `evaluation_object_class ∈ {posting_fact, reference_master}`, or an `le_bearing_flag`), set by a governed WRITER, with an AUTHORING GATE that makes it a hard PREREQUISITE before any CC LE-surface is stripped. **Version-pin rule (Codex gen-34e9bd-04):** activation and resolution read the `entity_version` PINNED to the CC/MC at authoring, so a later anchor `active_version_id` change can NEVER silently alter which COs require an LE stamp. The stamp/refusal and the activation gate read this version-pinned classification, never the mutable anchor and never an architect judgement.
- **Proof case: `customer_payment`** — a real posting-fact object (seed `ar-3103-canonical.json:11`, object-type `customer_payment`) with NO active CC today. Its `concept_registry.entity` row must classify LE-bearing MECHANICALLY (so a future `customer_payment` CC is stamped + fail-closed with no hand ruling). If it cannot classify mechanically against the named entity table, the discriminator is underspecified and the strip does not proceed. This is an OBJECT classification on the entity, never an LE value/axis on a contract (invariant intact).
