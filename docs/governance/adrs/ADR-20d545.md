# Curated-content export — relational reference canonicalization (W3 increment)

## Context

The W3 export mechanism (DEC-018138) canonicalizes a collection's rows by their **natural key**, excluding environment-volatile columns (generated uuids, timestamps, authoring-user). This was sufficient for the first collection — the governed vocabulary — because its rows are **flat**: their only identity is a text natural key and they reference nothing else.

Every remaining curated collection is **relational**: rows reference other rows by an environment-volatile uuid, in two forms —

- **Intra-collection hierarchy.** e.g. the metric directory: `group.family_id → family`, `member.group_id → group`. Verified live: `family` PK `family_id` (uuid) with natural identity `(function_slug, subfunction_slug, theme_code)`; `group` PK `group_id` (uuid), natural identity `(family, group_code)`; `member` PK `member_uid` (text) but `group_id` (uuid) → group.
- **Cross-collection references.** e.g. `group.grain_entity_id` / `member.measure_concept_id → concept_registry`; `member.realized_metric_contract_uid → mcf.metric_contract`.

A raw uuid is environment-specific (each environment generates its own), so it is not content and cannot appear in a canonical, cross-environment-parity export. The current export/reconcile has no reference handling; it must gain one before any relational collection can be exported or promoted. This is a cross-cutting, correctness-load-bearing change to the canonical form, so it is decided here rather than per collection.

## Decision

**In the canonical export, every reference (foreign-key) column is represented by the referenced row's declared natural key — never the uuid.** The raw uuid FK column is excluded as environment-volatile, exactly like a row's own generated uuid.

1. **Reference declaration, bound exhaustively to the schema (fail-closed).** A collection spec declares, per table, its `references`: for each FK column, the target table and the target's natural key. The export replaces each FK uuid with the resolved target natural key (a small object, e.g. `{ "family": {"function_slug": "...", "subfunction_slug": "...", "theme_code": "..."} }`) and excludes the raw uuid; a null FK exports as null. Because an *omitted* FK would otherwise be silently dropped as a volatile uuid — changing the content semantics and the digest — the tool **verifies the declared reference set against the table's actual foreign-key constraints in the source/target catalog** and refuses (export and promotion both fail closed) on any of: a schema FK with no matching declaration (omission); a declared reference whose target table/column does not match the actual FK (target drift); or a target natural key **not backed by a UNIQUE (or PK) constraint** on the target table (non-unique target → ambiguous resolution). The governed FK set is thus schema-verified, never hand-asserted.
2. **Canonical form stays uuid-independent.** Two environments holding the same authored content with different generated uuids export identically, because both rows and references are keyed by natural key. Ordering remains by natural key.
3. **Deterministic ordering; cycles refused.** The runner computes a **deterministic topological order** of the tables/collections from the declared reference graph (targets before dependents) and applies in that order, regardless of the manifest's listing order (an unordered manifest is accepted and ordered by the tool). If the reference graph contains a **cycle**, promotion **refuses fail-closed** (no deferred-constraint mechanism is introduced here; if one is ever needed it is a separately designed and tested unit).
4. **Fail closed on any unresolvable reference.** If a reference's target natural key does not resolve to **exactly one** row in the bound target state (missing or ambiguous), the promotion **RAISES and rolls back** (no partial apply, no release), inside the single activating transaction. A dangling reference is never written.
5. **Cross-collection references resolve against an explicit, digest-bound dependency (one invariant).** A collection that references another declares, in the manifest, the required collection **and its exact required content digest**. Promotion, inside the activating transaction, verifies that the referenced collection is **currently active at exactly that digest** — the digest recorded for it in the target's active release state (`content_release_collection`), re-confirmed against the referenced collection's current content — and **resolves references only against that bound state, never against ambient target rows**. If the referenced collection is absent from the active release, or present at a different digest (drift/stale), promotion fails closed. Intra-collection references (same collection, same activation) resolve within the transaction in topological order (point 3). This is the chosen closure invariant: an explicit active-manifest dependency with an exact required digest (not an implicit "present somewhere" check, and not a mandatory full re-ship of every referenced collection).

## Alternatives considered

- **Keep raw uuids in the export.** Rejected — uuids are environment-specific; the export would never achieve cross-environment parity and promotion would write foreign uuids that do not exist in the target.
- **Assign fixed/deterministic uuids to all curated rows.** Rejected — it would require rewriting live authored data to fixed uuids and fight the authoring path (uuids are generated at authoring time); natural-key references are the honest, non-invasive identity.
- **Let per-collection specs assert the FK set without schema validation.** Rejected — an omitted FK would be silently excluded as volatile data, changing content semantics and the digest. The declared set is verified against the actual schema FKs (point 1).
- **Dependency closure by full re-ship (every release contains all transitively-referenced collections).** Considered and not chosen as the invariant — it is self-contained but forces re-shipping large collections (e.g. mcf, source catalogs) on every dependent promotion. The chosen invariant (point 5) is the digest-bound active-dependency check, which is scalable and equally unambiguous. (A future release may still ship a closed manifest; the digest-bound check accepts that case too.)
- **Resolve references outside the activating transaction.** Rejected — resolution must be inside the single atomic activation so a concurrently-changing target cannot yield a dangling write; §6's one-transaction model already provides this.

## Required implementation-unit tests

The successor implementation unit(s) must prove, each **fail-closed with no release activation** on a disposable engine: an omitted FK declaration (schema-coverage refusal); a declared reference with target drift; a non-unique target natural key; a missing reference target; an ambiguous reference target; a wrong/stale active cross-collection dependency digest; an unordered manifest (deterministically ordered and applied); and a cyclic reference graph (refused). Plus the positive path: a hierarchical collection (metric directory) exports uuid-independently and promotes with all references correctly resolved.

## Not decided here

- The exact per-collection `references` declarations and natural keys (metric directory, concepts, source catalogs, contracts) — settled in each collection's implementation unit and there verified exhaustively against the schema (point 1).
- Serialization details of the resolved-natural-key reference object (beyond: canonical, key-sorted, uuid-free).
- Any deferred-constraint mechanism for cyclic reference graphs — out of scope; cycles are refused (point 3) until such a mechanism is separately designed and tested.

## Consequences

1. Relational curated collections become exportable and promotable with uuid-independent content identity — extending `build == dump == live` beyond the flat vocabulary to the hierarchical and cross-referencing collections.
2. The manifest dependency contract gains teeth: reference resolution is deterministically ordered, cross-collection dependencies are bound to an exact required digest of an active collection (never ambient rows), and any omission, drift, ambiguity, staleness, unordered input, or cycle fails closed rather than writing a dangling or mis-canonicalized reference.
3. The export/reconcile machinery gains one general reference-resolution mechanism, reused by every relational collection, rather than per-collection bespoke handling.
4. Each relational collection lands as its own reviewed implementation unit declaring its references; the metric directory (intra-collection hierarchy + cross-collection concept/mcf references) is the first exerciser.
