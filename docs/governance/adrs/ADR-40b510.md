# Demo-estate simulator v2 as a product (bc-demo): two-stream architecture, clone-and-strip, release-versioned governance

## Context

v1 (bc-sdg pilots/) accumulated as runbook drivers under per-revision byte-binding: 22 repair waves, r1-r60 runbook revisions, with defects migrating between layers (valuation -> reconciliation -> costing) because business events were never coupled to their full consequence chains and validation was blind to whole dimensions (a 700-day DSO passed every gate for 64 months; only an external benchmark + independent Codex audit caught it — adverse opinion). Each one-line fix cost a full governance cycle because drivers were not a released artifact. The product framing fixes all three failure classes at once: vertical lifecycles kill gap-migration by construction; closed-loop calibration to real sector ratios (Sundram/Bharat Forge/Endurance FY25 anchors) replaces invented plausibility bands; release-versioning collapses governance overhead to the release boundary where byte-binding belongs. The two-stream split is roadmap-driven, not speculative: D524 already names Microsoft BC as the second pilot source, and D561 commits to one flagship per domain-x-geography maintained lifelong — deliverable only by one product with N adapters and N profiles, never by per-estate script forks. Clone-and-strip (vs clean-in-place or greenfield) preserves the W1-W22 mining substrate and proven engines in-tree while ending cross-lane shared-working-tree hazards (bc-sdg stays untouched for the catalog lane; its TS ECC/SF simulator is a different product and stays canonical there). Second-system risk is controlled by two knowledge registers (KR-G global accounting/temporal facts; KR-S per-adapter quirks) that must become executable tests BEFORE dependent code, fed by v1 mining, systematic Odoo doc-mining (incl. 17->19 release notes), and a read-dont-build-on study of MIT-licensed Contoso/BCApps demo tooling (IDES excluded, proprietary). Prior-art survey found no occupant of this position: no existing tool posts through a live ERP application layer producing multi-year coherent, sector-calibrated, statutory-real, independently-audited books.

## Decision

The SDG's demo-estate capability is rebuilt as a software PRODUCT in a new repo bc-demo (cloned from bc-sdg with full history), replacing v1's 22 byte-bound repair waves of horizontal timeline-sweep scripts. Core decisions: (1) apex orchestrator with vertical event lifecycles, closed-loop shaped to externally-benchmarked realism targets; (2) TWO-STREAM architecture — GLOBAL business semantics (targets, locales, knowledge, validation gates) vs SYSTEM-SPECIFIC adapters (odoo19ee first; Microsoft BC second per D524) — mirroring the platform's own source-agnostic-contract philosophy; (3) clone-and-strip migration per operator-approved disposition registers (TS dual-simulator and ir-extractor stay canonical in bc-sdg, which remains untouched; v1 pilots tree frozen in legacy/); (4) RELEASE-VERSIONED governance — development under normal SDLC with day-one CI, governed estate-runs pin ONE SemVer release tag instead of 31 blob hashes, Codex reviews release candidates against acceptance criteria; (5) scoped checker service (monthly invariants / quarterly TTM drift / annual battery) so realism defects are caught within a quarter, not after 64 months; (6) product docs live in bc-docs per D234 (docs/implementation/demo-estate-simulator-requirements.md is the authoritative requirements + disposition register). v2.0 acceptance: parity with v1 greens + new working-capital/margin/clearing gates + Codex remediation criteria + determinism.
