# Database bootstrap source-of-truth model

## Context

Discovery under TSK-8e49e0 (Codex-accepted; re-baselined 2026-08-24 at bc-core 9828eede) established that the platform database has no single, honestly-documented source of truth. Multiple documents each claim to be authoritative and disagree with each other and the running system: docs say "three SQL files under docker/redesign/ define the schema" but ~200 files exist; docs point developers at a setup command (db:snapshot:restore) that targets a decommissioned container and cannot run; the schema is evolved by hand-applied change files with (until TSK-cd1dba) no record of what was applied; and some data (metrics, metric directory, business concepts) exists only inside a backup and cannot be regenerated. The absence of one declared source of truth has repeatedly cost sessions time chasing phantom drift (notably the monolith-vs-modular base-table drift). This decision fixes the truth first; it changes no code or data and authorizes no database change.

## Decision

For the platform database (bc_platform_dev and deployed equivalents), the authoritative source for each layer is declared as follows; nothing else may be described as "the authority" for that layer.

(1) CURRENT STATE — the live database is ground truth. What the running database contains is the authority on current state; no document may claim to define current state independently of it.

(2) SCHEMA-CHANGE MECHANISM — the platform schema files under docker/redesign/ (base 01/02/03 + numbered files + migrations/, ~200 total) are the authoritative mechanism for evolving the schema, applied in order. Every applied change is recorded in infrastructure.schema_migration_event, an append-only event log that records honest gaps rather than fabricated completeness (established by TSK-cd1dba). This log is the authority on what was applied.

(3) DRIZZLE IS A TYPE SURFACE, NOT THE SCHEMA AUTHORITY. The Drizzle definitions in src/database/schema/ are the app-facing type surface, regenerated by introspection. The Drizzle migration lineage is abandoned (frozen at 0038) and is not a schema-change mechanism. Where DDL/Drizzle diverge, the DDL and live database win.

(4) BASE-TABLE BLUEPRINT — the modular set is the source of truth. The modular directory docker/redesign/02-platform-tables/ is the SOURCE OF TRUTH for base platform tables (per DEC-1918d0) and is the fuller set. The monolithic 02-platform-tables.sql (the file Docker mounts on a fresh volume) MUST become a GENERATED ARTIFACT of the modular set and is NEVER hand-edited. The assembly mechanism (a generator, or mounting the modular set directly) is specified at the migration-baseline step. Interim rule until the generator lands: edit the modular set and keep the monolith in lockstep. The current split-vs-monolith drift is a recorded defect to be closed at that step; neither file is disposable.

(5) REFERENCE / CATALOG / CONTRACT DATA — seed:registry. The seed:registry pipeline is the authoritative generative source for reference, source-catalog, and contract data. The committed master/source golden snapshots are a cache of its output — an accelerator, never an independent authority.

(6) BACKUPS (full golden dump) — accelerator and recovery only. The full-database dump (local + S3) is an acceleration and recovery artifact, NOT the logical authority. It must become manifest-bound (recording what it contains and how fresh it is) before it may be relied on; that work is deferred. It must never be described as the source of truth for content.

(7) NON-REGENERABLE AUTHORED CONTENT — no reproducible authority yet. Metrics, metric directory, business concepts (mcf, metric_directory, bcf, concept_registry) are not reproducible from seed:registry today and survive only inside a backup. Providing a governed way to reproduce and promote them is the explicit purpose of the TSK-8e49e0 program (a future content-promotion step). Until then, this gap is stated, not hidden.

(8) STRUCTURAL RULES ARE PRESERVED AND VERIFIED. All applied database rules — constraints, foreign keys, indexes, immutability triggers, row-level security, check constraints — live in the DDL and ARE the bootstrap material. The migration-baseline step's acceptance gate is a from-zero rebuild whose schema fingerprint must match the live database (zero diff); this gate fails if any rule is missing, so no rule may be silently dropped. A rule that exists only because a migration was applied by hand (never captured in a from-zero file) must be caught by the baseline cutoff and witness-backfill and folded into the canonical baseline. Runtime/advisory locks used by the migration runner are part of the runner/role design, not schema, and are defined rather than lost.

(9) GOVERNANCE — retire the orphan code. The "D109" code cited by the disabled seed:v2 script and by CLAUDE.md has no ADR behind it and is retired. The authorities for database bootstrap are this decision together with DEC-5c39ea (as amended by clause 6).

RELATIONSHIPS (no supersession; no status flip): AMENDS DEC-5c39ea (the golden snapshot is an accelerator/recovery artifact per clause 6, not the primary logical authority). ERRATA over DEC-1918d0 (its "three SQL files" characterization is out of date per clauses 2 and 4). Statuses of both are unchanged.

CONSEQUENCES: the stale "authoritative" claims are corrected in the same change set (bc-core CLAUDE.md, DevHub CLAUDE.md, data-model-and-schema.md, infrastructure.md, deployment-topology.md; errata notes on ADR-09b8e6 and ADR-973363). Renaming docker/redesign/ to a non-historical name (e.g. docker/schema/) is a recognized follow-up deferred to the migration-baseline step (327 bc-core references + Docker init mounts make it a cross-cutting refactor, not a doc change).

SCOPE / NON-AUTHORIZATION: this decision is a truth declaration only. It authorizes no database change, code change, file removal, or backup/restore action. Every implementation wave (safe restore, migration baseline + runner, tenant upgrade path, content promotion, cleanup) requires its own review and Database Change Protocol approval, inside the D590-locked lane taxonomy, coordinating the drizzle/0022 touch-point with the Readiness program.
