# The exactness invariant governs all amount-producing operations — extend DEC-c4619b scope to the resolution layer

## Context

GROUNDING (bc-core origin/main @ 259ae6c4; ruling artifact RULING-resolveSum-binary64-vs-scaled-decimal-R2-2026-11-01.md @9c0d1a54):

1. The rule-system ALREADY EXISTS as one engine, one grammar, one obedience gate (the legacy `runNumericAggregate` compute path named in DEC-c4619b's annex has ZERO hits on origin/main — consolidation already happened; this ADR protects it, it does not create it). So the answer to the operator's general-form question ("shall we create a global metrics formula rule engine every formula obeys?") is NOT "build an engine" — that duplicates `FormulaExecutionEngine` + the exactness prover + `scaled-decimal.ts` and re-creates the very second compute path the consolidation removed (the rework trap) — but "extend the ONE existing rule's JURISDICTION."

2. `resolveSum` is a real binary64 amount-producing reduction OUTSIDE the DEC-c4619b declared scope: `const v = Number(raw); sum += v`, accumulator a JS literal `0`. Its output is AUTHORITATIVE — written once onto the primary/CO row by `copyMergedColumns` (:1571) and read by the evaluation engine as an already-collapsed single column; the engine never sees the addends and cannot re-prove the aggregation. Storage gives no rounding net: `ddl-generator.service.ts:106-107` types contract decimal/number -> Postgres bare `numeric` (no scale), so a binary64 tail persists verbatim (the exact drift DEC-c4619b documents). The downstream profile is fail-closed, not silent (`parseDecimalString` refuses nonzero digits beyond scale) — so a drift tail yields a hard eval stop or a non-EXACT label, never a silent cent miss.

3. It is a DOCUMENTED BOUNDARY, not a missed sweep: DEC-c4619b deliberately scoped to the evaluation engine ("storage schemas untouched"); the resolver `Number()` is in the resolution path that Decision left untouched. This is why it is the operator's doctrine call, not a mechanical bug fix: it asks whether "amounts never touch binary64" should hold at EVERY amount-producing boundary or only inside the evaluation engine as written.

4. Exactness bound worked for LC5 AR (DEC-545a4d prong a): a sum over n inputs scaled_decimal(scale=s,|x|<=B) is EXACT iff n*B*10^s < 2^53, provided each input is parsed to a scaled integer first. Policy `NUMERIC_DOMAIN_POLICY_V1` for (amount,decimal) = scale 2, |x| <= 10^8; B*10^s = 10^10; with a generous n = 10^5 lines/key, n*B*10^s = 10^15 < 2^53 (~9x margin). So `sumSameScale` over scale-2 BigInt cents is provably EXACT for LC5 AR — the gap is the REPRESENTATION (`Number()`+`+=` on decimal binary64), never the magnitude.

5. U4 (R2 AR) vs R4-scale: for AR Balance the `ci_doc_residual` sum collapses `asset_receivable` lines per (move_name, company_id). Single-contributor groups (one receivable line per invoice, the normal case) are provably exact -> match the LC5 oracle to the cent; drift needs >=2 contributing lines (multi-installment terms). So U4 is NOT a blocker, conditional on the multi-line-group count (the one open datum, read against `tbc_kaveri_dev`, folded into the U4 pre-emit gate), with fail-closed as the net. R4-scale is the real exposure: across the corpus multi-line sum groups are routine, so an unprofiled binary64 reduce becomes a broad recurring fail-closed blocker AND a standing dent in the DEC-346ae7 claim-3 mechanism story.

FOUNDATION (DEC-79b62f): this is a DESIGN/DECLARATION act (DEC-c48b0f), not a detector — the fix is declaring the invariant's jurisdiction; a detector at `resolveSum` would be the net, not the fix. Repair location B (the rule's scope/semantics), realized at D (resolution reducers) and later A (source-admission parse). Invariant at stake: VI (evidence emitted, not inferred) + the DEC-346ae7 claim-3 mechanism guarantee — an amount the mechanism PRODUCES must be produced under the exactness discipline the mechanism CLAIMS. No lower-layer compensation (DB hand-edit, NULL-store rounding) is acceptable; the fix belongs at the reduce itself.

RELATIONSHIP (amends, not supersedes — Architect call): DEC-c4619b is decided AND implemented; its mechanism is correct and in production. Superseding it would re-open a live, working ADR and (per hygiene rule 1) flip it to superseded, falsely signalling its mechanism is retired. The correct relationship is an amendment that widens only its declared scope. Therefore no `supersedes_ref` is set and DEC-c4619b stays decided.

## Decision

The deterministic numeric-execution invariant `scaled-decimal-int-v1` (declared by DEC-c4619b) SHALL govern EVERY amount-producing operation in the platform — formula kernels AND the canonical resolution layer's amount-producing reducers — through the ONE existing `scaled-decimal.ts` module under the ONE existing prover boundary. This EXTENDS (amends), it does NOT supersede, DEC-c4619b: that ADR remains decided+implemented and its mechanism (BigInt scale-pinned arithmetic, EXACT|REPRODUCIBLE|NOT_PROVEN verdict grammar, C9 admit gate) is unchanged and correct. Only its DECLARED SCOPE is widened.

SCOPE TODAY (DEC-c4619b): "the M10 fixture verifier (formula-execution engine -> v3) and the production metric evaluation engine; storage schemas untouched." The invariant's reach is thereby confined to operations INSIDE the formula AST. The canonical resolution layer produces canonical AMOUNTS before evaluation and is outside that reach by construction.

SCOPE AFTER THIS ADR: + ALL amount-AFFECTING operations of the canonical resolution + derivation layer — the ops that PRODUCE an amount AND the predicates that SELECT which amount is emitted. The governed set is enumerated below, but enumeration is a migration checklist, NOT the safety property (two review rounds each surfaced a site the inventory had missed); the safety property is the GOVERNED-OR-REFUSED invariant stated after the list. The enumerated set (audit-verified at bc-core 259ae6c4):

In `bc-core/src/boundary/ccv2-canonical-resolver.service.ts`:
- (i) secondary-join reducers: `resolveSum` (:1659, binary64 Σ via `Number()`+`+=`); `resolveLatestBy`/`latestByValue`/`strictNumericSelector` (:342, :1672) — a governed version SELECTION whose comparison runs on `Number()`-coerced doubles, so it must compare the selector decimals EXACTLY, not merely carry the winning row (two distinct large scale-2 values can compare equal after `Number()` and refuse a false tie).
- (ii) canonical derivations in the `computeDerivation` family: `computeLinearSum` / D514 `linear_sum` (:2331, `Number(raw)`+`+=`); `computeGroupSumWhere` / D517 `group_sum_where` (:2359), which carries TWO binary64 levels — the OUTER group accumulation `sum += sumDeclaredColumns(d,r)` AND the inner per-row `sumDeclaredColumns` (:2381) — both must preserve exact strings; `subtract` (:2271, `Number(minuend) - Number(subtrahend)`).

In `bc-core/src/registry/compute-evaluator.ts`:
- (iii) the delegated `sum_where` / `evalSumWhere` (:371), which returns a `Number()`-coerced canonical amount via `delegateToD330`.
- (iv) amount-AFFECTING SELECTION — `evalFilter` → `compareValues` (`:392-460`), the SINGLE shared filter path used by both delegated `sum_where` and the D517 `group_sum_where` row filter (resolver :2362): numeric `eq/ne/lt/lte/gt/gte` coerce BOTH operands with `Number()`, so a predicate can match or exclude the wrong source row and emit a wrong canonical amount EVEN WHEN the amount's own magnitude is in bound (gen-05b693-02 blocking finding — e.g. `9007199254740992` and `…993` compare equal). The predicates that gate an amount are governed too; this is the second inventory miss and the reason the safety property below cannot be enumeration.

A SECOND amount-producing class — source-admission numeric parse in the reader executors (`parseFloat` at `ecb-sdmx.executor.ts:162`, `fred-api.executor.ts:139`; repair location A) — is NAMED here and STAGED LAST, not folded into the first pass.

DECLARED OUT OF SCOPE (not silently skipped — named): date/day-count derivations (`date_diff`, `date_add`) and label derivations (`classify`) produce no amounts; the `Number(...)` sites in `resolved-admission-context.ts` are row-count/cardinality guards; string-identity filter predicates (`in`/`is_null`/non-numeric `eq`) select on identity, not amount magnitude.

GOVERNED-OR-REFUSED (the invariant made robust to inventory misses — the actual safety property): because enumerating "every amount-affecting site" proved fragile (each Codex round surfaced a missed path), the invariant is declared in FAIL-CLOSED form — every amount-AFFECTING operation (value production AND the predicates that select which value is emitted) is EITHER routed through the exact `scaled-decimal.ts` path under the prover OR fails closed to a recorded non-EXACT refusal. No amount-affecting op may silently emit on binary64. An un-migrated or newly-added site therefore cannot pass as EXACT by omission — it refuses until routed. The enumerated list above is then the migration order; the catch-all is what makes "governs EVERY amount-affecting operation" true without depending on the list being provably exhaustive.

REALIZATION PRINCIPLE (no rework, no second engine): route the named ops through the SAME `scaled-decimal.ts` module the engine already uses — replace `Number()`/`+=` with `parseDecimalString` (EXACT entry; the resolver holds the raw SQL numeric string, never a JS number) + `sumSameScale`, scale taken from the eval engine's `numeric-domain-policy` (already SELECTed at `resolvePinnedOcLeg:829` and discarded, recoverable with no new query). For D517 preserve exact strings through BOTH aggregation levels; for `latest_by` compare the parsed scaled integers exactly. `scaled-decimal.ts` BigInt arithmetic is exact at any magnitude — so a policy-pinned EXACT VERDICT is NOT automatic from routing alone: the prover must additionally CHECK the declared `numeric-domain-policy` bounds (per-item scaled magnitude `B·10^s` and contributor count `n`) and emit a recorded refusal / non-EXACT label past them. The `n·B·10^s < 2^53` inequality is the DECLARED-DOMAIN condition under which EXACT is granted — it keeps the SCALED INTEGER within the range exactly representable as an integer, so the proof's integer arithmetic is faithful; it is NOT a claim that the decimal value is losslessly recoverable through a binary64 downgrade (a decimal fraction generally is not — DEC-c4619b §5). Exactness is therefore preserved by carrying the exact decimal STRING, never by `toBinary64Downgrade` (which is lossy for fractions and is not on the exact path). No new module, no new grammar, no new engine; `FormulaExecutionEngineV3` remains the single exact-profile subclass of the single `FormulaExecutionEngine`.

STAGING (one stage per PR, Platform lane, resolveSum first): Stage 1 = `resolveSum` routed through `scaled-decimal.ts` + the prover extended to CHECK the per-item and contributor-count bounds (not merely perform exact arithmetic) with a recorded refusal/non-EXACT path + real-DB tests including values and groups just beyond each bound; carry the LC5-AR bound and the multi-line-group count as the U4 gate datum. Stage 2 = the remaining resolution/derivation amount ops — `computeLinearSum` (D514), `computeGroupSumWhere` (D517, exact through BOTH levels), `subtract`, the delegated `sum_where`, the `resolveLatestBy` EXACT-comparison correction, AND the shared `compareValues` amount-affecting predicate (exact type-aware comparison for numeric amount filters, or a fail-closed non-EXACT boundary where the predicate domain cannot be resolved — one fix covers both `sum_where` and D517 since they share `evalFilter`). Stage 3 = the source-admission `parseFloat` class (FX/macro, after a rate-scale policy is settled — FX rates legitimately exceed scale-2). The GOVERNED-OR-REFUSED catch-all (above) lands with Stage 1's prover so any un-migrated amount-affecting op fails closed from the first stage. Each stage is a named, labeled instance under this one declaration.

ROUND-TWO / TWO-ROUND-RULE NOTE (gen-05b693): the two Codex design rounds resolved the arithmetic-path omission (finding 1), the EXACT-verdict bound-check contract (finding 2), and the `latest_by` false-tie (finding 3). Round two surfaced the amount-affecting filter-predicate path (folded in above as (iv) + the catch-all) and invoked the standing two-round rule, so there is NO third Codex design round. This revision (the filter-predicate class, the GOVERNED-OR-REFUSED catch-all, and the wording correction) POSTDATES both rounds and is therefore NOT itself Codex-design-reviewed; it is submitted for the OPERATOR's close/re-scope decision. Each Stage implementation PR still carries its own Codex code review regardless of the design two-round rule.

STATUS = proposed. The decided-status flip and every merge remain operator-gated. Until this ADR is decided and Stage 1 lands, the resolver reduce is recorded as an explicitly labeled EXEMPTION to the DEC-c4619b profile (so it is never mistaken for proven-exact), guarded by the R2 U4 pre-emit gate (the multi-line-group count read against `tbc_kaveri_dev`). The exemption does NOT extend to R4-scale.
