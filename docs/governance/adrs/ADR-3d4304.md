# Source field typing for ORM/relational sources — governed data-type vocabulary + field-kind model (Odoo first)

## Context

The first Odoo contract-authoring attempt surfaced that the SAP-shaped catalog (flat scalar columns, free-text data_type_code) cannot faithfully represent an ORM source: 45% of account.move fields were mis-typed and relations/join-keys were flattened to strings, which would corrupt canonical resolution and admit phantom columns. The fix is a modeling decision (governed vocabulary + field-kind + what-counts-as-a-source-field), not a mapping tweak, and it sets the rule for all future relational sources — so it is recorded as a decision for operator ratification before implementation.

## Decision

**Context (measured 2026-08-08).** Odoo is the platform's first relational/ORM source. SAP tables are flat scalar columns, so the catalog's free-text `source_field.data_type_code` and implicit column-equals-field assumption were never stressed. The first Odoo SC/AC authoring over `account.move` (267 fields) exposed both breaking: 120/267 fields (45%) mis-typed — 84 relations (52 `many2one`, 20 `one2many`, 12 `many2many`), 19 blobs (`json/binary/html`), 17 `selection` enums — all flattened to scalar `string`; and the scalar coarsening produced `number`/`string` where the existing SAP catalog vocabulary uses `integer/decimal/binary/text/time`. Root cause: the UNIT-2 admission mapping (`dataTypeCodeFor`), NOT the extractor — the UNIT-1 extractor faithfully captured native `ttype`, relation target, and storage/derivation into `source_field_derivation`; the truth is preserved. No master vocabulary constrains `data_type_code`, so the drift went undetected. State is safe: the SC/AC version create failed (422) — nothing active; two orphan shells (`sc__odoo__account.move`, `ac__odoo__account.move`, 0 versions) exist; bad typing is confined to the one admitted account module.

**Decision.**

1. **GOVERNED DATA-TYPE VOCABULARY (from master).** Introduce a governed master list of scalar source data types (`master.source_data_type`: code, label, class ∈ numeric/temporal/text/binary/boolean/enum/structured); `source_field.data_type_code` FK-references it. This is the enforcement whose absence permitted the `number` drift — same discipline as the 5D source masters (D284) and other controlled vocabularies. Baseline codes reconcile SAP's existing set with Odoo's needs: `string, text, integer, decimal, boolean, date, datetime, time, binary, json, selection`. Source-agnostic: every source maps its native types into these codes (cross-source uniformity — Inv I, one meaning).

2. **FIELD KIND is first-class, orthogonal to data type — and NOTHING is dropped (operator direction 2026-08-08, Invariant VI).** `source_field` gains `field_kind_code ∈ {scalar, reference, relation}`. **Every** `ir.model.fields` entry is admitted as a `source_field` row, tagged with its kind and storage — the catalog is the source's full structural self-description.
   - `scalar` — a value field; carries a `data_type_code` from the master vocabulary. Observable when stored.
   - `reference` — `many2one`: a single-valued FK. `reference_target_object` = the target model; `data_type_code = integer` (the physical id); `cardinality = one`. Observable (the id) AND a join key.
   - `relation` — `one2many` / `many2many`: a multi-valued relation. `reference_target_object` = the target model; `cardinality = many`; relation linkage recorded (`one2many`: the inverse field on the target; `many2many`: the junction table + columns). No scalar `data_type_code`. NOT observed as a column value — it is **join/structure knowledge** the source emits.
   - `storage_code ∈ {stored, virtual}` is recorded on every field (already captured in `source_field_derivation`). Orthogonal to kind: a field is known regardless of whether it is stored.

3. **Why keep relations and non-stored fields (Invariant VI — evidence is emitted, not inferred).** The source *emits* its relational structure via `ir.model.fields`: `company_id` targets `res.company`; `line_ids` is the reverse of `account.move.line`. Dropping that knowledge here forces the canonical join layer to *rediscover* the join downstream — inferring what was already emitted, the exact reconstruction Invariant VI forbids, and a place errors enter. So the catalog **preserves** all relational and derivation knowledge at the layer that owns it.
   - This is a **declaration/observation split**: the catalog DECLARES the full source shape (all fields, kinds, targets, storage, derivation, depends, value sets); what the runtime OBSERVES is a separate, downstream selection. Observation defaults: stored scalars + reference ids flow into the chain; `relation` fields are join metadata consumed by the canonical layer (D508 / OC `join_semantics`) — not re-derived there; `virtual` (non-stored, on-read computed) fields are recorded and marked non-observable, so the runtime never depends on the source re-computing at read (Invariant I), yet the knowledge that they exist and how they derive is preserved. `store=true` computed fields (e.g. `amount_residual`) are observable scalars — D553 pt 8.

4. **`selection` is an enum, not a string.** `data_type_code = selection`; its value set is captured (extractor enhancement over `ir.model.fields` selection options) and feeds D513 coded-dimension classification at the canonical boundary.

5. **Normative Odoo ttype → (kind, data_type_code, cardinality) map — all admitted, none dropped:** char→(scalar,string) · text/html→(scalar,text) · integer→(scalar,integer) · float/monetary→(scalar,decimal) · boolean→(scalar,boolean) · date→(scalar,date) · datetime→(scalar,datetime) · selection→(scalar,selection) · binary→(scalar,binary) · json→(scalar,json) · many2one→(reference,integer,one) · one2many→(relation,∅,many; inverse field recorded) · many2many→(relation,∅,many; junction recorded). `storage_code` from `store`; observability derived from kind+storage per rule 3.

**Consequences / implementation (each its own reviewed unit or DBCP — NOT built here).**
- a. **DBCP**: `master.source_data_type` (governed scalar vocabulary) + `source_field.field_kind_code` + `source_field.reference_target_object` + `source_field.cardinality_code` + relation-linkage columns (or a `source_field_relation` child) + FKs; `data_type_code` FK is enforced where kind ∈ {scalar, reference} and NULL for `relation`. Applied AFTER reconciling existing rows (SAP set + the mis-admitted Odoo rows) to the vocabulary.
- b. **Fix UNIT-2 admission mapping** to the normative map: admit ALL fields with correct kind + storage + target + cardinality; scalars/references carry the governed `data_type_code`; nothing is routed away or dropped — the derivation facts remain the provenance companion.
- c. **Extractor enhancement (UNIT-1 successor)**: capture `selection` value sets and relation linkage (inverse field for `one2many`; junction table/columns for `many2many`); relation target + storage + derivation already captured.
- d. **SC field grammar**: add `kind` + `reference_target` + `cardinality` + an observability/selection marker (contract meta-schema change request per the D557/e1241a pattern, not a DBCP). The SC declares the full shape; the reader/OC selects what is observed.
- e. **Re-admit the account module** with corrected typing/kinds (extractor output unchanged → no new pilot_ent window); the corrected artefact supersedes; clean up the two orphan SC/AC shells.
- f. Only the account module is admitted; no other Odoo module is affected.

**Rationale.** A governed master vocabulary is the gate the free-text convention lacked (it catches exactly the `number` drift that occurred — governance-must-earn-its-keep). Keeping relations and non-stored fields as first-class, kind-tagged knowledge is Invariant VI applied to source structure: the source emits its shape; the platform records it once, at the boundary that owns it, so no downstream layer must infer a join it could get wrong. The declaration/observation split keeps this honest — full knowledge in the catalog, disciplined observation into the runtime (Invariant I). Precedent for every future ORM/relational source (Odoo, and the eventual BC/Salesforce readers), not a one-off Odoo patch.

**Status: decided (operator-directed 2026-08-08) — implementation is reviewed follow-up units.**
