# Reshape over immutable history: when the SO source table is also the validation oracle, prove on a disposable restore and admit forward-only — never re-admit or re-point live COs

## Context

The per-LE canonical-contract (CC) reshape for the Kaveri DSO must be proven correct, but the Source-Object source table it derives from — `so_sc_snedd` — is simultaneously the journal-entry-line SO table AND the source of the independent LC5 validation oracle. That dual role makes the obvious "reshape then re-admit on live" route doubly wrong: it would rewrite immutable Canonical-Object history (Invariant III) and corrupt the very oracle the validation compares against (Invariant VI — evidence is emitted/observed, not a thing the platform rewrote). The reshape was already proven to the cent on a disposable restore (SQL recompute of the declared formula over restored COs, 2026-10-24, evidence ~/bc-stack/evidence/c3-per-le-dso-restore-20261024/). This ADR states, as governed doctrine, which acts are permitted and which are prohibited, so the Metric lane's governed-evaluator prove-on-restore has an authority to cite. DESIGN ONLY — it authorizes no build, migration or live act; every execution unit keeps its own review + DBCP + operator gate. Governing authority: DEC-ffbc24/D673 (operator-locked LE pivot). Grounded 2026-10-24 at bc-docs origin/main c327c94.

## Decision

When a per-Legal-Entity canonical-contract (CC) reshape must be proven correct, and the Source-Object source table its Canonical Objects derive from is **also** the source of the independent validation oracle (the Kaveri case: `so_sc_snedd` is simultaneously the journal-entry-line SO table and the LC5 oracle source), the reshape is proven and admitted by exactly the two permitted routes below, and **never** by re-admission over live history.

**D1. The live source and its produced COs are the untouched oracle (repair B; Inv-III/VI).** The live SO source table and the Canonical Objects already produced from it are immutable and serve as the independent validation reference. No reshape act may mutate, delete, re-point, or re-admit over them. Re-admitting a reshaped chain on live would rewrite immutable history (Inv-III) and, because the same table is the oracle, would corrupt the very reference the validation compares against (Inv-VI).

**D2. Proof is on a disposable restore (PERMITTED).** Correctness of the reshaped formula/grain is proven on a disposable, read-only restore of a live dump — either an SQL recompute of the declared formula over the restored COs, or a governed evaluation run against the restore — compared to an oracle derived independently of BareCount's own formula. The restore is discarded; nothing it computes is admitted to live. Precedent: DEC-591eb7 ("live `bc_platform_dev` is the ORACLE, never mutated … scratch builds on disposable scratch_* only; read-only live via REPEATABLE READ READ ONLY"). This is the method used 2026-10-24 to prove per-LE DSO to the cent.

**D3. Admission to live is forward-only (PERMITTED).** The reshaped grain reaches live only as a NEW CC version with re-emitted Canonical-Object versions under the governed forward path (DEC-ffbc24 §7: sealed fact tables are never altered; re-emission, not in-place edit; iterate-per-LE). Each re-evaluation yields a new object version (Inv-V); prior versions coexist and remain addressable (Inv-III version coexistence). Supersession of the prior CC is a governance act that changes future use only — it does not modify or hide the retired versions.

**D4. Prohibited acts (named).**
- (a) in-place mutation of any Source Object, Canonical Object, or Metric Snapshot;
- (b) re-admission of a reshaped chain over live history;
- (c) re-pointing or re-binding active COs to a new shape;
- (d) deleting or overwriting prior snapshot/CO versions ("clean up the old shape");
- (e) any proof act that writes to the live source that is also the oracle.

## Invariants engaged

- **III — all state is immutable:** live COs are never altered; a reshape yields new versions that coexist with the old.
- **V — evaluation is non-replayable:** a reshape is a fresh evaluation producing NEW versions, never a replay or rewrite of prior ones.
- **IV — references are explicit:** the forward-only new CC/CO versions are named by identity+version; nothing resolves "head".
- **VI — evidence is emitted, not inferred:** the oracle source stays observed and untouched, never platform-rewritten, so the validation compares against a real external figure.

## Foundation gate (DEC-79b62f)

1. **Why this location (B — contract/evaluation-method semantics)?** It declares the governed method (allowed vs prohibited acts) for proving and admitting a reshape when source == oracle. It is a semantics declaration, not a detector.
2. **Why not an upper layer (A)?** Admission and CO production are already correctly specified (COs are immutably produced from SOs). The gap is a missing governance DECLARATION about re-admission-vs-restore; that belongs at B. A fix below B would be lower-layer compensation for an unstated rule.
3. **Why not a lower layer (D–F)?** A runtime guard that merely blocks live re-admission is a net, not the rule. The declaration must exist first; enforcement can follow as its own execution unit.
4. **Design act or execution act (DEC-c48b0f)?** DESIGN ACT — it supplies a missing declaration (forbid live-reshape when source == oracle; mandate disposable-restore proof + forward-only admission). It is not a detector and makes no behaviour correct by itself.

## Scope and status

Applies to any chain where the SO source table is also the validation oracle source; the Kaveri per-LE DSO reshape over `so_sc_snedd` is the motivating case. This ADR authorizes no build, migration, or live act — each execution unit keeps its own review + DBCP + operator gate, consistent with DEC-ffbc24. **Status: proposed.** Ratification is the operator's recorded grant; proposed status is not authority to act.
