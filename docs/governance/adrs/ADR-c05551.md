# Governed legal-entity dimension: separate canonical identity from per-source company key via a source-to-entity binding

## Context

The fiscal Odoo re-base (Codex F2a) exposed that dim_legal_entity's value-equality join silently assumes the source emits the same company code the tenant admin declares as free text. That assumption is a known, explicitly-parked D367 scope item ("populating tenant dims from source systems") that was never picked up. It holds for SAP BUKRS (a meaningful, human-known code) but breaks for Odoo, whose company identifier is a surrogate integer with only a nullable/non-key company_registry label — verified first-hand: pilot1 has 0 dim_legal_entity rows, only a '*' fiscal calendar, and no source-to-entity binding table exists anywhere. The legal entity is the axis the entire read model turns on (every canonical object carries a recording/issuing legal-entity reference; metrics group by it; the portal apex filter IS it; consolidation unifies the same entity across sources), so fixing it fiscal-locally would build the binding layer once per consumer — the lower-layer compensation Foundation forbids (Invariant I: meaning produced once at its boundary). Resolving identity once, at the canonical boundary, via a governed binding keeps the runtime source-agnostic and makes the apex filter, metric grouping, and multi-source consolidation all correct by construction.

## Decision

Separate the tenant's canonical legal-entity identity from any one source system's company key, and add a governed binding between them. (1) A legal entity has a stable tenant-canonical identity; the recommended form adopts the platform identity doctrine (D560 — opaque uid is the authority, legal_entity_code/display_name become labels, not the join key). (2) A governed, versioned, attested source-to-entity binding maps each source system's company COORDINATE (the stable key: SAP BUKRS, Odoo res.company.id, Tally company id) to the canonical entity, with cardinality supporting many source-companies to one entity (branches, multi-source consolidation). This closes the scope D367/DEC-8672d0 explicitly deferred ("Populating tenant dims from source systems — OUT this ADR"). (3) The binding is applied at the canonical resolution boundary so facts carry the canonical entity code (source-agnostic); fiscal resolution, metric grouping-by-entity, and the portal apex company filter all read the one dimension. (4) An admitted source company with no active binding is a recorded onboarding/admission refusal, never a wildcard — completeness is a governed gate. (5) This supersedes D367's implicit assumption that dim_legal_entity.legal_entity_code equals a source company code (a value-equality join that holds only for SAP-style meaningful codes and breaks for Odoo's surrogate res.company.id / nullable company_registry); the equality is retained only as the degenerate case where a tenant chooses to reuse a meaningful source coordinate as its legal_entity_code. Reuses existing substrate (dim_legal_entity shell, BCF Legal Entity entity 3bd1857e / DEC-f4e9a0, company_code shared BF / DEC-68f2c7); the only genuinely new substrate is the source-to-entity binding plus governance on how dim_legal_entity is populated. Open forks carried to the design thread and Codex review: opaque-uid-now vs binding-only; binding table placement and grain; the bc-admin onboarding mapping surface and its completeness proof. Design-only; anchors the thread DESIGN-legal-entity-dimension-source-binding-2026-08-16 (barecount-devhub@852429d). No code, schema, or DBCP authorized until Codex disposition and operator approval.

## Boundary (Codex ACCEPTED WITH BOUNDARY — bc-external-audit@b4f6abb4, sha256 267c1594)

The **principle** (points 2–4 above) is accepted and this ADR is `decided`; the following boundaries constrain and, where noted, **amend** the proposal. No code, schema/DBCP, binding authoring, contract mutation, activation, or live action is authorized by this record. The next reviewable unit is a head-pinned **A0 binding-substrate + realization design** closing B2–B4.

**B1 — no opaque-UID migration in A0 (amends point 1).** `legal_entity_code` REMAINS the D367 primary/join key, consumed by fiscal config, canonical facts, snapshots, and semantic-family expectations. Recasting it as a mutable label is NOT accepted here. A later, separately-reviewed identity migration may add an opaque tenant-entity ID — it must define the key transition, every foreign/reference and evidence surface, historical-query semantics, and rollback. It is not an A0 prerequisite. (My "opaque-uid-now" recommendation is withdrawn for A0.)

**B2 — closed source-instance provenance coordinate (retains fiscal F2b).** The proposed `(source_system, source_object_version, source_key_value)` grain is INSUFFICIENT — two Odoo installations under one tenant can share `res.company.id`. The A0 binding lookup identity MUST be built from actual runtime provenance: the resolved tenant connection/installation coordinate (`connection_id` or an equally durable resolved coordinate; source facts join `progression.admission` → `progression.admission_run` which carries it), source-contract UUID **and** version (not names + a free-text `source_object_version`), the pinned source object/leg coordinate, and the source key — all taken from source-fact/admission provenance. Uniqueness and lookup MUST use that identity; vendor/table names are not substitutes. The CC-v2 resolver reads `__reader_id`/`__run_id` but its public input has only tenant/CC/env/limit — A0 must specify how the connection coordinate reaches lookup.

**B3 — enforceable temporal/governance/realization/evidence semantics (retains fiscal F2c–F2d).** `is_active` + free-text `attested_by_name` + a partial-active unique index do NOT provide the required properties. A0 MUST define and enforce: (a) an immutable binding-revision model + an explicit as-of coordinate (e.g. admitted observation time or a justified source-time); (b) non-overlap and **exactly-one-applicable-row** behavior over the full binding identity, failing on zero OR multiple matches; (c) an authenticated governed authoring/approval/supersession path (an actor identity + governance event, not a text field); (d) capture of the selected binding ID/revision + its source-provenance tuple in canonical evidence/lineage, so a later binding change never makes an existing CO's LE realization unreproducible (Invariant III/VI). A0 MUST also specify the ADDITIVE canonical mapping grammar, activation validation, runtime lookup service API, refusal timing, and adversarial tests — the resolver today has only `direct` + static `code_lookup`; `classify_by_binding` is GL-only and not runtime-wired. A table alone will not transform `res.company.id` into a canonical Legal Entity reference.

**B4 — onboarding is the single DEC-103acb completeness path.** DEC-103acb already mandates governed tenant-dimension writers (incl. `dim_legal_entity`) + an identity-completeness gate blocking `active` (`onboarding_incomplete` state). The source→entity mapping EXTENDS that one path: every entitled source-company coordinate must be bound + attested before a chain that can emit it may run. No second free-text admin route; runtime admission alone does not make an incomplete tenant ready. Refusal boundary (chosen in A0/runtime design): preflight verifies binding coverage; canonical realization refuses a fact whose provenance-scoped lookup has zero or multiple matches. (pilot1's empty `dim_legal_entity` is the DEC-103acb Phase-C grandfather case.)

**Fiscal scope note.** Fiscal successor-2's proposed `organization.source_legal_entity_binding` table is **NOT** accepted as an implementation design (fiscal successor-2 = CHANGES REQUIRED, F2b–F2d). Fiscal B/D is a **consumer**, held behind this shared binding design; it does not own or ship the binding.
