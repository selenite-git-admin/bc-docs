# Fiscal-calendar window is half-open [effective_from, effective_to); the '*' calendar row is retired by refusal

## Context

- No governing document declared the boundary: D364, D368, D623 and D162 R9 are silent. The signals conflicted: the DDL CHECK effective_to > effective_from forbids a one-day inclusive window, and ADR-e44afd's sibling grant window is half-open, while the served resolver and the revision rules were inclusive.
- The governed revision path is append-only, so a row's natural end is the next revision's effective_from. Half-open makes abutting rows assign each date exactly once.
- Live impact: none. No fiscal_calendar_config row has effective_to set (Kaveri's two rows are both NULL).
- Operator decision 2026-09-27 (TSK-7b8df6, TSK-008655): given by the operator in the GEN Exchange Master chat (recorded in RESPONSE-Codex-gen-b6cabe-01) and confirmed by the Platform Readiness umbrella the same day.

## Decision

1. organization.fiscal_calendar_config.effective_to is EXCLUSIVE. A row applies on effective_from and on every later date up to, but not including, effective_to; NULL means open-ended. Every reader of the window (the D623 resolver FiscalCalendarService.resolveCalendarConfig, the D504 revision rule pickCalendarInEffect, the E6-B in-transaction proof re-pick verifyProofScopeInTx, and the proof reader's K10(d)) uses ONE shared predicate, bc-core src/registry/fiscal-calendar-window.ts. A class guard, src/__architecture__/fiscal-calendar-window.spec.ts, fails on any hand-written comparison. The boundary day is outside: the writer refuses an act whose as-of equals effective_to, and K10(d) fails it (this closes design gap G-2).
2. The hand-edited legal_entity_code '*' row (tbc_kaveri_dev, 2026-09-23 operator-approved exception) is NOT end-dated. It is immutable history: it stamped the pre-D623 canonical objects. It is already unreachable, because the resolver matches the exact legal entity and refuses '*' before any lookup (WildcardLegalEntityRefusedException, D623 / DEC-ea4523). Its retirement is that refusal, with no DB write. Setting effective_to would itself be a hand mutation (Invariant III).
