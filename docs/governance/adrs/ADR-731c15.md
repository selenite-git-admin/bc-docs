# Pilot source-infra pre-staging workstream — BC + Odoo on AWS, build-prove-hibernate; parallel to platform, metric-independent

## Context

The pilot's slowest external dependencies (getting realistic data into a real BC/Odoo and proving we can read them) are entirely independent of the metric-definition churn and the r23 fork, so they can be de-risked now instead of serially after the platform settles. Self-hosted BC container sidesteps the 30-day SaaS free-period limit and the free/paid cliff, at only compute cost. AMI-and-terminate hibernation makes the parked environment cost ~a few dollars/month while preserving instant resurrection with data intact — matching the cost-lean default. Keeping the scope strictly metric-independent preserves the D524 Track-C hold on governed contract work and avoids manufacturing rework against a platform whose definitions are still in flux.

## Decision

Founder-decided 2026-07-29. Establish a pilot source-infrastructure pre-staging workstream that runs in PARALLEL to the platform/MCF program, scoped strictly to the metric-INDEPENDENT source-side prerequisites for the D524 BC+Odoo pilot.

WHY NOW: platform metrics are not ready (PLN-457cd0 v6 — the semantic-audit r23 fork is open and gates the wave order; tenant runtime is empty by design; source-feed readiness is "the true ceiling"). The platform's own doctrine (D498/D499) already decouples metric definitions, runtime data-readiness, and source-system infrastructure. This workstream parallelizes the source-side so the pilot's slowest external dependencies are de-risked and parked, without racing the moving platform.

SCOPE (metric-independent only): (1) stand up BC + Odoo instances; (2) generate faithful multi-year synthetic data through each vendor's own posting/APIs; (3) prove connector reachability — Odoo XML-RPC/JSON-RPC read; BC self-hosted basic-auth read. EXPLICITLY NOT in scope (stays Track-C-gated, D524 hold intact): SC/AC/OC/CC authoring over BC/Odoo, metric authoring, or any governed contract-chain work. This does NOT un-hold D524; it only pre-stages the instance+data+connector prerequisites.

HOSTING + LIFECYCLE: both on AWS EC2 (barecount profile, ap-south-1), decoupled from the machine-global local Docker-engine contention that repeatedly blocked the local BC build. BC runs as a SELF-HOSTED Windows container (BcContainerHelper) — no 30-day SaaS clock, free dev/test license, pay only compute. The BC SaaS 30-day trial is reserved solely for the later OAuth2/Entra connector-auth proof (self-hosted BC uses basic auth). Cost pattern: build → generate → prove → bake an AMI of each instance → terminate → hibernate. Idle cost ≈ AMI/snapshot storage only (~$4–5/mo both); resurrect ~10–15 min on demand. One-time build/test ≈ $10–15. Cost-lean standing default honored.

SEQUENCE: Odoo E2E first (cheap Linux, proves the pattern), then BC E2E (Windows, heavier).

THIRD SYSTEM: the D524 pilot pair remains BC + Odoo. Oracle Fusion is NOT a third pilot and is NOT viable for this workstream (no free/self-hostable instance — Oracle-subscription-only SaaS); it stays the deferred documentation-only enterprise-optics fallback. If a third axis is later wanted, Salesforce Developer Edition (permanent free org, CRM domain) is the near-zero-cost option, as an addition to D524.

CLAIM BOUNDARY: standing BC/Odoo up green is necessary but NOT sufficient for a "green pilot" — the last mile (contracts + metrics computing through the chain) is platform-coupled and Track-C-gated. This workstream pre-stages prerequisites; it does not make the pilot green.
