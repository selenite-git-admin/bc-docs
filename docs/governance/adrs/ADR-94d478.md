# One-time pre-launch reset of the old metric corpus on the development database, delete with a read-only copy

## Context

The owner's rulings of 2026-11-23 (DECISIONS, 20:05 and 20:10 IST, yes to a, b and c; 20:46 IST, "yes, copy and delete the members"): the old corpus in the catalog and directory is confusing and cannot be used; archiving was rejected because a status protects only the reader who checks it, and sessions misread archived rows; deletion protects every reader. The corpus was authored under rules since overtaken (DEC-89db41: brownfield as supply, greenfield as trust; DEC-21ca17: pre-certification actives are raw material), so its content is kept as raw material in the copy, not as state in the platform.
Foundation, named honestly. Invariant III: once produced, an authoritative object is never altered and all versions coexist; no version is erased within the execution model. Invariant VI: Evidence and Lineage are immutable and append-only. This act erases governed versions, certificates, demo-plane Metric Snapshots and 4 plus 4 Evidence and Lineage rows. It is therefore recorded as what it is: an act on a pre-launch development database outside the execution model, holding no customer record, done once, recorded by this ADR and one ledger event, with every removed row preserved byte-faithfully twice (the verified backup and the sealed copy). No Foundation text is amended and no exception clause is used (owner: no bypass via notes, exception or special approval). If review holds that a Foundation erratum is needed, the act stops and the question goes to the owner.
Proof: bc-db pull request 187, rehearsal GREEN 19 of 19 on an owner- and grant-faithful restore of a fresh read-only dump (the copy made and verified before the delete; every kept row of the eight reached schemas unchanged; no kept uuid column names a removed identity; the served logins read the empty corpus without error and cannot reach the copy). Design: barecount-devhub artifacts/operator-review/DESIGN-metric-reset-2026-11-23.md revision 3 (content commit 8fa6f83c).

## Decision

1. One time, on the development database bc_platform_dev only, before launch, the platform's old metric corpus is removed: every metric contract and version (all 464 as read on 2026-11-23, customer invoice volume v1 e6438795 and the successor draft 74f1f2e0 included) and everything built on them: bindings, filters, panel runs and transcripts, certificates, auditor exchange records, the demo proof plane built on them (hand-over, custody, runs, evaluations, Metric Snapshots, proof pins, and the 4 metric Evidence and 4 metric Lineage rows), the metric directory's realization ledger and legacy migration records, every metric directory member and every row keyed to one (member versions and their parts, feasibility results and references, member knowledge, and the directory decisions about a member), the metric-side panel outputs, the tenant metric provisioning commands, and the life-cycle events that resolve to nothing. The act is bc-db forward migration 0079 (one transaction, one ledger event) run through its apply kit docs/dbcp/apply-0079 under the owner's recorded desk grant.
2. Before anything is deleted, every removed row, and the before-image of every row the act changes, is copied into a separate database on the same server, bc_metric_raw_material, owned by a NOLOGIN role, closed to PUBLIC, sealed read-only, read by no served code. The copy is verified set by set (count and fingerprint equal to the platform's in the same snapshot and to the reviewed pins), and the delete itself locks every affected table and refuses unless each set still reads those pinned fingerprints, so the deleted bytes are the copied bytes. The channel's first step reads it only through one named command, whose login is granted later by its own act. Nothing in the copy carries trust, whatever a status column in it says.
3. The directory keeps its taxonomy: its families, groups, their versions and the family-level decisions stay, and the one channel creates each of the ~900's members afresh in them (owner, 2026-11-23 20:46 IST). Kept pointers to removed rows are cleared in the same transaction: the old-lane status (back to candidate) and the three links on the seeds that carry them. The concepts registry, the seed catalogue's content, the source, observation and canonical contracts, the demo world's canonical rows and configuration are not touched. Tenant databases are outside this act.
4. The delete guards of the deleted tables are paused by name inside the one transaction and enabled again before it ends; the paused list is pinned and must equal the catalog's own list; foreign keys stay enforced.
5. A verified pre-apply backup (restore-verified on a throwaway clone) is taken by the kit and held to the retention end named in the grant. The copy bc_metric_raw_material and its two roles are removed, by a granted act, once the ~900 demo-world metrics are active in the platform catalog.
6. This reset is never repeated. From now on every metric enters through the one channel, and every correction goes through the execution model (new versions, supersession), never through deletion.
7. The decided status of this record needs the owner's recorded desk grant.
