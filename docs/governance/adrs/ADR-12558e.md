# Odoo 19 EE is a JSON-RPC Connector over http transport with an OdooJsonRpcProtocolReader executor, reusing basic auth

> **Implemented (code unit) 2026-08-10** — bc-core PR #675 (merge `d78e1747`), Codex disposition
> ACCEPTED-WITH-BOUNDARY (SHA-256 `3E8BA6B6…58168373`). Landed: `OdooJsonRpcExecutor` (read-only
> authenticate→uid + execute_kw search|read, company context, → RunObservationItem[]), registered as
> `OdooJsonRpcProtocolReader` in `BoundaryModule`; 10 unit tests; no DTO/DB/resolver change. **Still
> held as a separate authorized execution unit (Codex boundary, out of this unit):** catalog-row
> registration (`odoo-jsonrpc` + `odoo-ent-v19`) and the rung-1 reachability proof on `pilot_ent`.
> Reader Flavor/Connection remain behind the OC hold (D555); the live-source Scanner is Part 2 (DEC-7a18af).

## Context

Modelling JSON-RPC as http (not a new transport enum) is the minimal-surface choice that is also literally correct: Odoo JSON-RPC IS an HTTP POST. It avoids a create-connector.dto enum change and any DB migration, so the whole of Part 1 is code + catalog rows, nothing schema-level. Reusing the `basic` auth strategy is likewise minimal-and-correct: Odoo authenticates with a login+password pair, which is exactly what `basic` resolves; inventing an `odoo`/`jsonrpc` credential strategy would be net, not fix (the resolver already produces the needed shape). db and url are connection-target facts (flavorConfig / connectionEndpoint), not secrets, so they do not belong in the credential resolver.

Foundation: repair-location A (source reality / admission boundary — the Connector is HOW the source is reached), executor implemented in the reader-runtime boundary (D). DESIGN act (D541): authoring the connector capability + executor is the design; registering the rows and proving rung-1 against pilot are the execution acts that follow disposition + operator authorization. Invariant VI (evidence emitted, not inferred): a reachability claim is proven by an observed login_uid and a re-read record, never asserted. Invariant III (immutable / non-replayable): the executor is strictly read-only (search+read only; S-32 never writes state), so observation cannot mutate source state. No invariant conflict.

Anchors: DEC-731c15 (pilot workstream explicitly releases Odoo connector-read proof; schema authority = Odoo-19 vendor source; live pilot_ent is read-only) and DEC-95687d (Connector is the primary onboarding trigger — this connector is the head of the eventual chain-walk, though the walk stops at SC/AC while OC is held). Transport reference is bc-demo/simulator/adapters/odoo19ee/client.py, which has exercised ~40k live JSON-RPC calls against this host — its transport semantics (S-40 JSON-RPC, S-4/S-34 company context, G-7 read-to-prove) are ported, not reinvented. The two-tier catalog (generic protocol + source-bound) mirrors the live odata-v2/sap-odata-v4 precedent, keeping the Odoo connector shape consistent with what already exists. Alternatives rejected: (a) a first-class 'jsonrpc' transport_type — rejected, needs a DTO+DB enum change for no semantic gain since JSON-RPC is http; (b) a new odoo credential strategy — rejected, basic already yields {username,password}.

## Decision

Odoo 19 Enterprise is onboarded as a platform Connector modelled as follows:

TRANSPORT — `transport_type='http'` (NOT a new 'jsonrpc' enum value): Odoo JSON-RPC is an HTTP POST to `/jsonrpc`, so the existing http transport is correct and no create-connector.dto enum widening / DB change is required. `protocol_name='odoo-jsonrpc'`, `protocol_category='proprietary'` (matches the salesforce-soql/tally-xml precedent — execute_kw is Odoo-specific, not a universal protocol), `executor_class='OdooJsonRpcProtocolReader'`, `supported_auth_methods=['basic']`, `generation_method='hand_built'`.

CATALOG ROWS — two, mirroring the existing odata two-tier pattern (generic `odata-v2` + source-bound `sap-odata-v4`): (1) a generic protocol connector `odoo-jsonrpc` (category='protocol', sourceSystem null), and (2) a source-bound connector `odoo-ent-v19` (category='enterprise', bound to the odoo provider_id/system_id, system_version='19.0'). Both authored via the official `POST /connectors` API — no direct DB inserts. Lifecycle starts `draft`; promotion to `available` follows the rung-1 reachability proof.

EXECUTOR — a new `OdooJsonRpcExecutor implements ReaderExecutor` in `src/boundary/reader-runtime/executors/odoo-jsonrpc.executor.ts`, registered by `executor_class` into `ExecutorRegistryService` in `BoundaryModule.onModuleInit`. It ports `bc-demo/simulator/adapters/odoo19ee/client.py`'s transport into TypeScript: JSON-RPC `common.authenticate(db, login, password) -> uid`, then `object.execute_kw(db, uid, password, model, method, args, kwargs)` for `search` + `read` (paginated via limit/offset), with company context (`allowed_company_ids`/`company_id`, S-4/S-34). It maps each record to a `RunObservationItem` (sourceKey = id + company, `observedPayloadJson` = record, `provenanceJson` = {source:'odoo-jsonrpc', endpoint, db, model, uid, fetchedAt}). Plain `fetch()`, no npm dependencies. READ-ONLY: it never calls create/write/unlink and never writes `state` (S-32). It faults the whole class of XML-RPC None-marshalling bugs by using JSON-RPC (S-40).

AUTH — reuse the existing `basic` credential strategy unchanged: it already returns `{username, password}`. The executor consumes `auth.username` (Odoo login) + `auth.password` (Odoo password) + `flavorConfig.db` (Odoo database name) + `connectionEndpoint` (Odoo base URL). No new CredentialResolverService strategy is added in Part 1. The pilot secret is provided to the runtime at execution time (env/SSM credentialRef, or the host file for the container-internal proof) and never committed.

SCOPE — Part 1 delivers the two catalog rows + the executor + a rung-1 reachability proof (container-internal `execute_kw` on `pilot_ent`). A runnable Reader Flavor + tenant Connection + live observation run are DEFERRED: a Reader Flavor requires an Observation Contract, and OC/CC/MC are HELD under D555. The live-source Scanner is Part 2 and depends on the parked field-capability ADR DEC-7a18af. External-URL reachability (rung 3) is a separate operator-gated step, not part of this decision.
