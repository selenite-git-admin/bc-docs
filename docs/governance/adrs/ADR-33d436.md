# Platform Readiness & Legibility — program mandate, platform/tenant readiness split, and SSOT consolidation

## Context

The program's authority was two files in the wrong repo (`bc-core/docs/design/platform-functional-refactor-{plan,package}.md`) while the converging Platform DB Foundation program had a clean bc-docs SSOT. The concepts (tracks, lanes, planes, the readiness definition) were scattered across those files, the locked lane taxonomy, the convergence map, and the design/execution-plane finding — and the platform-vs-tenant readiness distinction was conflated (the Kaveri pilot, a *tenant*-MLS walk, was being used as the *platform* readiness proof). A single SSOT plus this mandate fixes both. Operator-ratified 2026-09-19.

## Decision

The Platform Readiness & Legibility program (anchor TSK-4b2404) is consolidated into a single SSOT at `bc-docs/docs/implementation/platform-readiness-program.md` (+ `overview/platform-readiness.md`), superseding the bc-core R4 design docs `platform-functional-refactor-{plan,package}.md`, which become pointers. The program's canonical model:

1. **Readiness = `streamlined · governed · documented · proven-once-E2E`** — all four required, mapped across tracks (streamlined = T, governed + proven-once-E2E = R, documented + legible/no-black-boxes = L). It is **two-layered** along Metric Lifecycle States (MLS, DEC-c9e623): **PLATFORM readiness** = MLS 01-14 / lanes L1-L9 + runtime-engine conformance, provable on a fixture/sandbox tenant (no customer onboarding); **TENANT readiness** = MLS 15-25 / lane L10 + the runtime (the Kaveri pilot), a downstream milestone that depends on platform readiness AND the Platform DB Foundation program. This corrects the prior framing that treated the Kaveri tenant walk as the platform proof.

2. **Three cuts:** 4 tracks T(closed)/R(the gate)/L/S(deferred) as the work axis; 10 locked lanes L1-L10 (DEC-a67bae/D590) as the ownership/artifact-family axis (source-onboarding and tenant-onboarding are workflows over lanes, not lanes; L10 reclassified as the platform→tenant boundary lane at MLS-14→15); design-plane vs execution-plane (DEC-c48b0f).

3. **The current critical-path gate is Track R** (runtime Foundation conformance + governing the execution-plane couplings), fixture-provable and decoupled from DB Foundation — **but Track R is not sufficient for platform readiness alone**; Track L's documented / no-black-boxes criterion is co-requisite.

4. **Operator UI coverage per lane/workflow is a first-class readiness criterion** (no black boxes, the *documented + legible* criterion — Track L, co-requisite with R). Mapped gaps (L8 Registration/Directory = full black box, L9 chain-audit = no door, L10 tenant configuration/health/scoping/infrastructure = stubs) are the Track-L door-walk backlog.

## Change Procedure

Amendments follow the Decision and Change Procedure. The detailed SSOT (`platform-readiness-program.md`) is the living authority; this ADR locks the mandate and the platform/tenant split.
