# Source-catalog admission scope: only real source objects; non-table models are contamination, rejected at admission

## Context

Found during the account-module SC/AC authoring batch (SES-d2236e, 2026-08-09): all 41 admitted objects were typed object_type_code='table' with a default 'id' key, but ~6-7 are abstract mixins / transient / report / SQL-view models with no observable source rows. Authoring source contracts for them yields dead contracts; more fundamentally, letting them into the catalog at all is contamination. Operator doctrine (2026-08-09): "non-table/non-object elements should never enter the catalog — otherwise they are contamination." Inv I (meaning is evaluated once, at its boundary): admissibility must be decided at admission, not re-litigated by a downstream SC/AC eligibility filter — a downstream filter would be lower-layer (C/D) compensation for an upper-layer (A) admission-boundary gap, which the Foundation gate forbids. Root cause of the gap: admission hardcoded objectType='table' (extract-admission.build.ts:189), ignoring even the extract's existing transient flag, and the extractor captured only transient — not abstract or view. The correct fix is at A: reject non-source models at admission so the catalog only ever contains real source objects.

## Decision

The source catalog admits ONLY real source objects — persisted tables that emit observable rows. Non-source models are CONTAMINATION and MUST be rejected fail-closed at the admission boundary; they never become source_object rows:
- abstract models (_abstract=True — mixins, e.g. account.document.import.mixin, sequence.mixin): no table, no rows.
- transient / wizard models (_transient=True — e.g. account.move.send) and report models (e.g. report.account.report_invoice): ephemeral, not a system of record.
- SQL views (_auto=False — e.g. account.invoice.report): queryable but DERIVED (an aggregate of a real source such as account.move.line); BareCount computes such aggregates itself, so a source view is a derived duplicate, not a source of truth.

Admissibility is a function of the vendor model kind, captured by the extractor from the source-system registry (Odoo: _auto, _transient, _abstract → model_kind ∈ {table, view, transient, abstract}) and enforced at the admission gate. Only model_kind='table' is admitted; the rest are refused with a recorded reason. object_type_code is derived from the admitted model kind, never hardcoded.

Enforcement layers: (1) extractor emits model_kind; (2) admission (extract-admission) rejects non-'table' kinds fail-closed — no source_object/source_field is created for them; (3) already-admitted contaminants are removed via a governed path (not hand-edit; the D557 delete guard refuses deleting approved rows, so removal is designed, e.g. soft-delete or a guard-aware DBCP).

This EXTENDS DEC-3078ce (D557) catalog-onboarding — it does not supersede it. D557's admit→verify→approve lifecycle is unchanged; this scopes WHAT is admissible.
