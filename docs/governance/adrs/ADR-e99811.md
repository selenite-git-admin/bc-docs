# The served engine login reaches the demo plane only through two named pin doors

## Context

See decision text below.

## Context

Migration 0087 created the demo world pin routines `demo.fn_pin_world_metric_version` and `demo.fn_pin_world_cc_version`, owned by `bc_schema_owner`, SECURITY DEFINER, with EXECUTE granted to no login. Today only a superuser under `SET ROLE bc_schema_owner` can pin, and no served command can. Its build note 1 deferred the caller "to a later, reviewed grant", and its postcondition forbids the served platform login from reaching schema `demo`.

DEC-89db41 (the D575 generalization to runtime planes {tenant, demo}) states the demo-plane rule: the plane is reached only by its own logins, with no direct or indirect reach from the platform plane. DEC-b269fd amended it for the guarded proof-write login `bc_demo_prover`; DEC-1bb88e made the demo plane a resolving plane. Neither names a served platform reach.

The owner ruled on 2026-11-26 "Build the command" (barecount-devhub branch claude/operator-review-content, `artifacts/operator-review/DECISIONS-workflow-review.md`, commit 6c7cff31): build a governed served command so every later metric uses the pin with no per-metric grant. The owner then gave the database yes for migration 0090 (same file, commit 68ecc9c8, answer "Yes, build 0090") on the Chief's proposal `pin-command-proposal-2026-11-26.md` (section 2.2, option A).

## Decision

1. Two new SECURITY DEFINER routines, `mcf.fn_pin_world_metric_version` and `contract.fn_pin_world_cc_version`, each call the matching 0087 `demo` routine unchanged. EXECUTE is granted to `bc_platform_runtime` only.
2. The canonical door refuses a label that has no first canonical pin yet. First pins of a label stay the owner's act; only disjoint additions go through the served door.
3. The served commands are `pin-world-metric-version` and `pin-world-cc-version`, each with check and do, role `mcf_publisher`. They set `declared_by_name` from the signed-in identity, never from the request body.
4. `bc_platform_runtime` gets no USAGE on schema `demo`, and no other demo reach: no table privilege and no other routine. The served login's reach is exactly these two named routines (the precedent is `contract.fn_cc_version_is_world_pinned`, 0087 note 1a).
5. Every 0087 trigger (writer guard, chain, seal and state, one live version at commit, immutability) still decides each pin. The command re-implements no rule; its early refusals are readouts.
6. No table, row, login, secret or other grant changes. Rollback drops the two routines. The migration is bc-db `0090_world_label_pin_served_doors`.
7. This record extends DEC-89db41 for these two routines only and supersedes nothing. The demo plane stays otherwise reached only by its own logins.

Authoring only: the engine-hold exception, the auditor landing, the merge and the live apply each still need their recorded grant. The owner's acceptance of the served login's reach by name is this ADR's decided status, which needs its own recorded grant.

## Rationale

- Foundation gate (DEC-79b62f). Location C (binding): which exact metric contract version a world label proves is a declaration of the binding. The record and its rules exist (0087); what is missing is a governed executor.
- Why not an upper layer: contract semantics (B) and the source boundary (A) are complete for this act; nothing semantic is underspecified, so this is not compensation.
- Why not a lower layer: nothing working is bypassed. The doors call the 0087 routines unchanged, so every trigger still decides. It is not an evaluation (D) or a storage edit (E), and no row is hand-edited.
- Design act (DEC-c48b0f): it declares the executor of an already declared act by naming the login, which is the reviewed grant 0087 note 1 deferred. It also amends the plane-boundary posture of 0087 note 1 and DEC-89db41 for exactly two named routines.
- Invariants: III (pins are immutable; a change is a successor pin), IV (exact FK references, predecessor named), VI (the pin row is the emitted evidence). Reads never trigger evaluation.

## Consequences

- The served platform login gains one deliberate write reach into the demo plane, for two kinds of records (metric pins, disjoint canonical pins). The W6-P G10 pin gate of 0087 goes from 19 to 21 EXECUTE pins for this login, and bc-core's grant-drift TSV gains two lines.
- `declared_by_name` and `authority_ref_text` are trusted by the routines, so the command must source them from the identity and the standing grant (ead781aa).
- The command fails closed (`pin_door_absent`) if served before 0090 is applied.
- Delivery order: bc-db PR for 0090 with rollback, kit and restore proof; bc-core PR for the command; one auditor landing (Lane: platform); one live window (apply 0090, then serve-move).

## Alternatives rejected

- B. EXECUTE on `demo.fn_pin_*` straight to `bc_platform_runtime`: needs USAGE on `demo`, crossing the plane boundary that 0087's postcondition forbids.
- C. `bc_demo_runtime`: refused by standing gates (SELECT-only reader; 0054, 0051 P4); it would turn the reader into a writer.
- D. `bc_demo_world_handover`: a bc-demo tooling login not in bc-core; it would mix the answer custodian's duty with choosing the version the world proves.
- E. A new login with a CLI runner (D575 pattern): most separation, but needs CREATE ROLE, an operator-set secret per DEC-ecd55c, and a runner for every pin, so it cannot be a served command and does not meet "every later metric with no per-metric grant".
- Leaving the canonical door out of 0090: rejected; one review, one G10 regeneration and one live window is cheaper, and the first-pin refusal keeps the owner's act.
